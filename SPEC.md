# m365crawl specification

## Archived Teams cached-compose bodies

`drafts list [--include-removed] [--limit N]` and
`drafts show teams-draft:HASH [--body-revision DIGEST] [--include-removed]`
MUST read only the selected archive/account. They MUST NOT acquire, refresh,
discover, register, migrate, fetch, start a browser, hydrate, mutate app data,
send/edit/discard or enter shared search/messages/thread/unread/activity/FTS.
`--max-age` is syntax-validated but acquisition-inert. Explicit CLI acquisition/
link flags MUST be rejected, unused inherited live-source values ignored.
List alone supports fields; explicit empty fields on show is still invalid.
Show supports max-text, including explicit0 for full text. List defaults50 and
text preview300 Unicode code points; show defaults full text/unexecuted HTML.

Source eligibility requires exactly one `|`, nonempty profile other than `.`/`..`
without slash/backslash/NUL, and ASCII origin matching
`^https_teams\.(microsoft\.com|cloud\.microsoft)_[0-9]+$`.
Preserve exact source strings; this syntax is not archive authenticity or live
profile attestation. The existing Teams database parser MUST establish exact
manager/store and nonempty tenant/user matching archive envelope. Qualify
`streams-replychain-manager/drafts` object members only after complete wrapper/
key/member-namespace validation. Two nonempty wrapper-key strings MUST equal
wrapper conversationId/replyChainId. Member key and nested message.id MUST be
nonempty but MUST NOT be required equal. Creator and activity sourceUserId MUST
both exactly equal `8:orgid:<envelope user>` with Boolean isSentByCurrentUser true.

Required exact tokens: `type=Message`, `draftType=RegularDraft`,
`threadType=streamofdrafts`, `messageType=RichText/Html`, `contentType=Text`,
unquoted numeric token `state=0`, activityType/activitySubtype `Draft`.
State0, lieType Send and false flags are format tokens, not lifecycle meanings.
Let U mean EXACT object `{"$undefined":true}` with no extra members, N native null.
All following fields MUST be present with these representations:

| Field | Required representation |
| --- | --- |
| clientDraftProperties.scheduledSendTime | N |
| properties.sendAt; sendPipelineStatus; sendPipelineOAMState; streamingMetadata; skypeeditedid; originalNonLieMessage | U |
| lieType | exact string Send |
| clientDraftProperties.isForwardedMessage; forwardPrivateReply | Boolean false |
| clientDraftProperties.forwardAppIdsToInstall; forwardMessageIds; forwardMessageRecipients | exact string `[]`, not native array |
| clientDraftProperties.forwardMessageCardContents | exact string `null`, not native null |
| clientDraftProperties.forwardMessageCardsCount; forwardMessageOriginalConvId; forwardTeamId | N, not zero/string-null |

Missing/U/N/wrong type/token MUST withhold except exactly as shown. Do not
recursively decode serialized strings, normalize whitespace or interpret unknown
optional client properties. Body authority is message.content ONLY; preserve
readable/empty/missing/undefined/null/invalid, with no activity-preview fallback.
Existing HTMLToText provides a cached projection, not native editor rendering.
Native lastEditTimestamp is checked numeric integer milliseconds; fractions,
overflow/strings stay invalid. VersioningTimestamp is independent string/presence;
archive first-seen/update/removal clocks are not editor/server clocks.

ID is `teams-draft:` plus FULL lowercase SHA-256 of deterministic Go JSON encoding:
`["teams-draft-id-v1",source,tenant,user,database,store,canonical_key_json,member_key]`.
The key string is the exact archived canonical key, not reformatted JSON.
Body revision is FULL lowercase SHA-256 of deterministic Go JSON ordered frame:
`["teams-draft-body-v1",identity_tuple_json_string,actual_complete_retained_wrapper_utf8_string,removed_boolean,removed_at_string_or_null,decoder_qualification,projector_qualification]`.
Initial qualifications are `teams-draft-decoder-v1` and `teams-html-to-text-v1`.
No content_hash shortcut or normalized wrapper semantics. Metadata/conversation/
advisory/receipt clocks and archive updated_at are excluded. Every success states
`body_guard_scope=retained_wrapper_body_frame_only`, `target_guarded=false`.
A guarded call can return changed target/title. A→B→A can reuse its digest;
there is no immutable/monotonic history or overwritten-body recovery.

One read-only transaction MUST cover descriptor/fetch/body/association/
conversation/coverage. Before materializing ANY payload/key/identity/used auxiliary
string into Go, SQL MUST report native type and `length(CAST(column AS BLOB))`.
Require allowed types, per-input8MiB, cumulative64MiB PRECHARGED before fetch/
decode, repeated SQL type/length guards on fetch, at most4096 visited rows and
4096 visited message-map members across phases. Include ALL used conversation
id/kind/title/team and source/run strings. Null/presence is not empty text.
Cancellation and SQL/I/O/schema failures remain failures. These policy caps do
not bound RSS/CPU or represent operator-supplied thresholds.

Relevant association universe is ALL same exact source/account
messaging-slice-manager/drafts-metadata-items across locale/removal. Require
three nonempty exact sourceThreadId/sourceMessageId/clientMessageId equalities;
two usable supplied sourceReplyChainId claims cannot conflict. Wrapper is not
target. Exhaust possible matches before unique/resolved. A capped/malformed/
oversized possible match makes association incomplete, even after one match.
Missing/ambiguous/incomplete metadata permits an independently complete own body.
Conversations are auxiliary account-scoped archive evidence, NOT same-profile/
capture/UI evidence. Full resolution requires completed consistent auxiliary lookup;
removed association is historical. Preserve Space team-side, Topic channel, Chat.

Incomplete requested frame MUST emit no body/token; unsuccessful incomplete scope
MUST yield teams_draft_scan_incomplete, not unknown. A complete own body can succeed
with unrelated/global/association incompleteness. Eligibility precedes removed,
completed eligible-identity ambiguity and revision mismatch, in that order.
Foreign/non-own/unsupported ids share teams_draft_unknown with absent after complete
scope; no per-id withholding/native identity leak. Aggregate diagnostics are scoped,
not requested-id dependent. Exact body totals, including0, require complete body
scan; prefix ordering never implies newest/global completeness. draft_coverage
survives fields/limits/clipping/zero, with body/scope/association completeness,
lower-bound/unknown losses and independently qualified source/account clocks.
Advisory counts never substitute totals. Not-marked-removed can contain old bytes
after source decode failure; removed never means sent/discarded.

Ordinary full_inspection MUST preserve exact absolute selected DB, account,
removal opt-in, ID and body guard with max-age0/max-text0 and safe platform shell
quoting. `full_inspection_shell` MUST identify `posix` on non-Windows hosts and
`powershell_7_3_standard` on Windows. The Windows command requires PowerShell7.3+
(`pwsh`), guards that minimum version, and scopes Standard native argument passing
to its invocation. It is NOT cmd.exe, a batch command or Windows PowerShell5.1
syntax. All variable arguments use verbatim single-quoted literals, doubling
ASCII apostrophes and interpreted smart single quotes (U+2018–U+201B); dollar,
backtick, percent/exclamation environment tokens and Windows-valid Unicode path
characters MUST round-trip unchanged through the actual shell/native argv.
No selected valid path is refused or replaced by a placeholder. Missing-archive
show retains generic teams_draft_unknown plus ID-independent selected-archive-
missing context, never an acquisition remedy. No raw SQL/full client blob or
misleading --revision alias is required.
Native qualification remains one fresh Mac Space/team-side body and removed
historical Chat shapes only; not current chat/UI/editor/server-unsent, native
Windows, app-version/lifecycle/key continuity or all-drafts completeness.
Source-wide host-object omissions have unknown per-draft-store allocation.

## Native calendar attendee evidence (schema 19)

`calendar attendees sync [--root DIR | --source-id ID]` MUST be explicit.
Default discovery is Mac HxStore; a supported copied profile root is portable.
This does not qualify Windows/OWA native acquisition. `sources`, `list <event>`
and `show attendee-observation:N` MUST open only the selected existing archive
read-only, never refresh, register, copy, migrate or repair, even at expired
max-age. Source selectors and observation IDs are positive archive int64s;
new archive IDs/native64 values use exact decimal string transport.

Native observations describe the reader-selected detail group of an actual
successful calendar decode. They MUST NOT replace, filter or re-count the
retained/unioned displayed calendar roster, response, room or Teams fields.
They do not resolve subjects, establish tenancy or prove current membership.
The fixed scope is `native_source_selected_detail_not_display_roster`.
An unchanged source-local unlinked scope may display unscoped; it does not
satisfy a Teams account filter.

The actual calendar winner path emits requested-only receipts after successful
mapping. Distinct raw event IDs mapping to one public UID remain distinct.
No second winner algorithm or pre-emission candidate cache is permitted.
Auxiliary charging precedes filters: at most524288 selected objects and65536
detail keys, including unused/resynced ones. Overflow clears all optional
bookkeeping/rows with `outlook_attendee_selection_too_large`, retaining healthy
legacy output. Unrequested receipt state stays nil.

Owned evidence is immutable canonical JSON with fixed order, strict unknown/
duplicate/noncanonical refusal and nullable literal text preserved. The limits
are262144 native observations,65536 receipts/geometry keys,262144 bytes per
native scalar,16MiB combined name/email bytes and8MiB combined selected IDs.
Attempt-scope strings are individually262144 bytes and jointly1MiB; census is
4MiB and transports every Stats scalar and all three bounded pair maps.
The384MiB evidence envelope exceeds the counting-writer-proven266MiB maximum;
there MUST NOT be a hidden smaller budget. Readers check SQL byte length
before body/census materialization. Health auditing streams the full relevant
canonical model with bounded relationship/ambiguity state, not full attendee
DTO arrays merely to show source health.

One additive schema19 stores `outlook_calendar_reads/read_state`,
`outlook_link_events/link_state`, and
`outlook_attendee_sources/requests/snapshots/occurrences/bindings/members`.
Every successful ordinary calendar decode, including an unregistered one,
allocates a unique atomic immutable read ID. Equal/backward/known-zero clocks
are not identities; unchanged checks allocate none. Receipt digests use
canonical component arrays and retain original-offset known-zero read clocks.
Standalone origin conflicts, existing unknown origins and unknown continuity refuse
before calendar overwrite, mail invalidation or positive native admission. A
genuinely new partition is distinct from an existing unqualified one. Old unknown
origins bootstrap only through eligible actual ordinary decode without mapper
bump or rich-detail blanking; recovery preserves the selected archive and exact
requested Outlook root, requires verifying the original source, and never forces
full-read or bypasses the copy interval.
Source-ID recovery obtains a separate original root only from validated admitted
request history of that source, including when newer requests are source-ID-only.
The retry request remains exclusively source-ID. No admitted root means explicit
bounded unavailability, never a guessed locator parent or widened discovery.

Link mutation identity uses AUTOINCREMENT events plus an independent current
frontier, account-qualified FK and explicit null baseline. Exact owned table/
trigger definitions, missing state/tail and wrong-account references are
audited before zero hits/filtering and before a writer can repair them.
A→none→A at repeated clocks cannot regain old scope.

Snapshots and physical rows are stored once. A-B-A reuses A's snapshot/physical
IDs and first clocks, with new request/read/link/census/attempt membership.
Representation identity binds qualification, decimal source ID and complete
owned evidence, not the input-file hash, census or attempt clocks. Membership
digests protect those separate fields, exact request, read receipt, captured
owner/link revision and streamed binding/occurrence index. This is corruption
consistency, not authentication against coordinated digest rewrites.

Native association resolves actual typed `(source,account_id,source_id)` rows,
aliases/joined keys, origins, reads and link/native frontiers in one transaction.
Merged UIDs, subjects and all accounts of a principal cannot select a parent.
Namespace intent is audited before projection. Body audits cover current
candidates for default reads, associated retained candidates for history, own
snapshot for detail, and admitted bodies supplying source counts. Unrelated
undisplayed history is not certified. Reuse/new admission cannot hide or repair
corrupt old evidence. Own-snapshot ambiguity survives parent/100-row/field
projection and remains identical in store, shape, text, JSON and full SQL.

One guarded private copy/lifecycle owner stages all eligible readers and closes
them before verified cleanup, then independently admits optional lanes.
Lane-local failures do not poison a healthy peer; common cleanup/cancellation
prevents optional positive admission. Diagnostics are bounded to10 seconds on
WithoutCancel. Ordinary capture uses registered lanes only and never repeatedly
recopies merely to repair optional native state. Standalone invalidates the
mail-read marker before advancing the shared fingerprint, without reading or
erasing mail; the next eligible ordinary unchanged-input read still captures
mail. The common five-minute interval and single outer archive lease remain.

`native_attendee_evidence` is independent of fields, zero hits and item limits.
Explicit-account read notices distinguish source profile provenance from the
compatible captured/current linked owner required by native list/show. Empty
scoped results do not prove absence of archived evidence. Sources remain
archive-wide diagnostics, not owner-filtered by `--account`; `--source-id` only
narrows list/sources, never show. Source-local inspection requires an explicit
repeat of the same read/selected archive/ID without `--account`, changing
inspection scope without proving ownership or current membership. There is no
automatic retry or acquisition. Account-scoped unavailable detail keeps exit2
and `outlook_attendee_unknown`; its generic message/fix is identical for valid
absent, foreign and unlinked IDs and comes from request context only. Existing
corruption/audit/error precedence and the separate sync-account refusal remain.
Bindings are separate bounded previews, not duplicated people. First100
physical observations retain full totals; copied display-name clipping never
changes literal stored text, email claims, native IDs or another result.
Full-record SQL extracts one indexed native attendee JSON object with own
losses/ambiguity; full capture reads the snapshot separately. Independent
`own_captures` recovery routes name the positive own snapshot IDs of previewed
rows/bindings, including historical detail. They survive fields, deduplicate at
most200 IDs (100 rows plus100 bindings), and never substitute current source
coverage for an old capture or embed full source blobs per row. Every executable
route MUST preserve the selected absolute `--db`, `--max-age 0` and full
unclipped SQL payload. Initial failures retain nullable source ID and the exact
original request, never a guessed parent directory or source ID0.

## Engage Home-session archive (schema 18)

The concrete `engage_home` content family MUST follow the
[Engage evidence/clock/lifecycle contract](docs/engage-home.md).
`content fetch engage-home` has no target arguments and captures only the fixed
native root/Home access-session path. Product browser defaults and the delivered
45/30/10/3-second bounds and retained-string/cardinality limits MUST NOT increase.
Early capability checking and registration precede acquisition navigation;
verified terminal Close and cancellation barriers precede publication.

One additive migration18 stores immutable canonical complete bounded Result JSON
(64MiB ingress/read envelope above the proven51,576,832-byte maximum),
source-bound mapper digests, first physical acquisition/admission clocks, ordered
occurrences, every successful attempt membership and exact typed FTS.
Account boundary is canonical `[Host,NetworkID,UserID]` plus
`engage-native-home-v1/mapper-v1`, never a Teams identity.
Identical A-B-A sessions reuse A occurrence/session IDs and first clocks, while
appending membership; changed order/metadata/clocks/flags/losses changes identity.
Every successful session is partial; complete frontier MUST remain NULL.
Metadata-only differs from empty admitted blocks and MUST retain old readable history.

Every zero-Result/discarded-candidate failure MUST be registration-level
account-unknown. A-success → B-success → unknown failure MUST retain A/B own clocks,
coverage and pointers. The historical last-successful-instance pointer MUST NOT
be labeled active/current signed-in account. Coverage is body-free and independent
of fields/limits/zero hits. Detail carries original-session losses separately;
losses MUST NOT be attributed per thread or multiplied per hit.

Reads MUST audit all canonical results/accounts/duplicate columns/digests,
original/intermediate/reused membership, outcome/loss/coverage/reason, frontiers
and exact occurrence FTS provenance before filtering. Stream session history with
cancellation and check blob length before decode. Ordinary reads/reuse MUST NOT
repair corruption. Optional old-schema absence is read-only empty coverage;
current missing/partial tables are errors.

Only native starter-updated time orders/filters Engage text. Preserve original
raw strings and JSON-serializable offsets, including UTC-year10000/-1 spill.
Use range-safe Time comparisons, never UnixNano or derived UTC text as a
parser/order/filter key. Pointer/raw flag presence distinguishes known Go-zero
from absence. Existing family ties precede Engage; new ties use full label,
source/session/ordinal/numeric archive ID before clipping.

Every mixed content/shared-search comparison MUST put known clocks before unknown
clocks, then compare native instants newest-first with range-safe Time comparisons,
then apply established family/tie order. Engage's explicit presence retains a known
Go-zero; legacy hits without independent presence retain zero-means-absent semantics.
This deliberately changes the exceptional old legacy unknown-versus-pre-year-one
order: unknown no longer precedes a known early instant. Normal legacy chronology
and equal-clock family precedence are unchanged; stored clocks/IDs/bytes do not change.
Text lists MUST render differing column schemas as separately labeled consecutive
tables, preserving selected row order. Registration outcome/account_state/reason/retry
MUST NOT be printed under instance source/current_session/coverage headers.

`engage-observation:N` is a positive archive occurrence ID. Preview is first100
ordered blocks with empty/duplicate occurrences preserved; clipping copies
slices/pointers and never alters full native IDs/flags/version/raw clocks.
`full_text_sql` uses only the generated positive archive ID to join the full
occurrence and original session Result in the same archive, never a native ID.
No fabricated URL/person/document/task join is allowed.
The additive `full_text_command` MUST preserve the selected absolute archive and
`--max-age 0` alongside the exact static SQL, so a follow-up cannot refresh a
different/default archive. Fetch receipt projection MUST audit history without
materializing all historical observations; `EngageAttemptReceipt` returns only
the admitted current attempt's body-free source and ordered occurrence IDs.
An unspecified Store snapshot output limit defaults to128 with `Truncated`;
this is not a lower ingress/producer budget or a history-validation shortcut.

Exact-root/default443 agreed sign-in has a five-minute productive deadline,
preliminary Home readiness and one native observer verification only with at
least45s remaining. It discards content and has no archive admission side effect.
Positive native evidence plus successful Close is required; generic unavailable,
redirect, identity and timeout remain auth-unknown. Native interactive expiry/
challenge and live Windows/Linux service behavior remain unqualified.

## Explicit cloud content (schema 16)

The concrete SharePoint/Stream backend feeds only explicit one-target
`content fetch page URL` / `content fetch stream URL [--transcript-id ID]`.
Page targets are `/sites/NAME` or `/teams/NAME` modern `SitePages/*.aspx`;
Stream targets are the same site's `/_layouts/15/stream.aspx?id=FILE_PATH`.
HTTPS, validated SharePoint host and once-decoded path/selection identity,
8192-byte URL, 4096-byte path and 256KiB requested transcript bounds remain
the backend's contract. Canonical safe requests preserve the admitted raw
path/id encoding, normalize host/443 and discard every nonidentity query.
Locator identity is ordered JSON kind/host/site/path/transcript string-or-null,
never an unescaped delimiter or original sharing ticket.

Only the tool-owned normal profile captures headlessly. Allocate an attempt under
a short exclusive archive lock; release/close that store before browser launch.
Close the exact owned browser before reacquiring publication lock, on success,
failure, cancel or panic. Cleanup/cancel wins over staged data. A wrapper failure
publishes no candidate. No silent interactive sign-in; `content signin URL
--user-agreed` is the explicit admitted-site-root workflow. Diagnostics are finite
fixed codes, never raw browser errors, URLs or content.

Existing knowledge locator/attempt/source machinery supplies the monotonic
publication frontier. A cloud registration binds kind/platform/canonical locator;
an instance additionally binds host/site/web/file/account ID/LoginName as literal
JSON tuple components. Caller-requested selections register separately. Native
selected transcript IDs belong to bodies, not metadata boundaries. Native
file/account changes cannot borrow another instance's last-good body.

Schema 16 adds `cloud_locator_metadata`, `cloud_observations`,
`cloud_capture_members`, `cloud_capture_metadata`, `cloud_source_body_state` and
`cloud_fts`. Full typed backend result JSON and reader qualification determine
immutable representation digest. A-B-A reuses A's original ID/capture/completion
clock. Current verified metadata and last-good-body pointers update atomically.
Later metadata-only/empty/denied states carry null selected transcript, preserve
old body T with its own evidence and report selection unavailable; later body U
leaves historical T explicitly differing. Fatal attempts record diagnostics only.
SourceObservedAt is null. Acquisition completion is not native modification.

Pages always have partial scope, including empty supported projections. Stream
complete scope `selected_transcript` means one verified selected body with no
losses, never collection/service completeness. No-transcript and selection-required
states are verified metadata, not invented transcript objects. Backend limits remain
eight reads, 2MiB each/8MiB combined, 1MiB selected text, 256KiB retained string,
4096 controls/65536 DOM nodes/depth128, 128 collection items/16384 entries.
Write and read validation reuse the backend typed finite contract; corrupt state
is refused, including at zero hits.

Content reads, sources and content-only shared search are archive-only on every
max-age: no migration, browser, auth, source app file or implicit retry. Old
read-only schemas expose optional absence. FTS indexes supported retained text,
titles and native metadata. Filter source_id by admitted instance, and retry
registration_id only with explicit fetch. Unknown native modified clocks fail
bounded date windows. Content order is known modified newest, full title, source ID,
numeric observation ID. Shared timestamp ties preserve every pre-existing family's
relative order, put cloud afterward, and only cloud/cloud ties use full unpreviewed
native keys before the final global limit.

Account/author/chat/mail-only/profile filters reject explicit content and exclude
it from all with a notice. Coherent content_coverage stays outside item fields and
global clipping, includes failed/unadmitted/metadata-only/no-transcript sources and
does not assert no content at zero hits. Detail ID syntax is positive decimal
int64 `cloud-observation:N`. First100 native ordered control-text/entry occurrences
are previews, totals and clipping explicit. Native transcript/entry/requested IDs
are at most128 Unicode-rune `native_id_prefix` with `native_id_truncated`; full
values remain archived. Full structured follow-up is static SQL over generated
positive internal rowid in this same database, never native text as SQL.

`content_unknown` is a usage error: inspect sources/list or explicitly register a
supported target. `content_signin_required` is a usage error: obtain user agreement
to content signin, then retry explicitly. Other browser/database errors retain
existing fixed codes. Native Windows service acquisition is unqualified; portable
offline reads and synthetic tests are not native acceptance claims.

## 1. Purpose and scope

m365crawl lets an agent on a supported desktop host read the operator's Microsoft Teams history quickly and offline. It mirrors the new Teams desktop app's local cache into a local SQLite archive with full-text search, then answers queries from that archive. Its primary users are agents, so it favors predictable commands, stable JSON, coded errors with a `fix`, and self-diagnosis over interactive features.

It never talks to the Teams service, never reads or uses Teams credentials, and never writes to Teams' storage. m365crawl's own code opens no network connection except to the loopback port of the Chrome DevTools Protocol (CDP) of a browser it started: only explicit `transcripts fetch`, `transcripts signin`, `content fetch page/stream` and `content signin URL` reach SharePoint through the tool-owned browser profile. Other commands are offline; ordinary content reads are archive-only regardless of max-age and never fetch or sign in.

In scope for v0.2.0:

- macOS and Windows with the new Teams app (`com.microsoft.teams2` / `MSTeams_8wekyb3d8bbwe`), every WebView2 profile, every Teams origin and every signed-in account found in them.
- Conversations (chats, channels, teams, meetings), messages (channel posts, replies, chat and meeting messages), the activity feed, read state, and people derived from message senders and conversation members.
- Every other Teams IndexedDB database that does not look like credential material (pinned messages, contacts, call history, the calendar stores and the rest of what the app caches), mirrored generically into the `records` table; the calendar stores also feed the typed calendar tables.
- The Teams calendar (events, meeting recaps and action items), derived from the generic records, and the new Outlook for Mac calendar as a second source that is read by default when it is installed (section 4.2).
- Meeting transcripts: the parts of every recorded meeting, listed from the recording notices already archived, and their speaker-attributed text once `transcripts fetch` has stored it; `transcripts`, `transcripts show`, `calendar event`, `search` and `status` read it offline.
- Explicit cloud content: one supported SharePoint page projection or selected Stream transcript, with verified metadata and retained bodies read offline; not a library crawl or rendered-page export. Native Windows acquisition remains unqualified.
- Commands: `doctor`, `whoami`, `sync`, `status`, `search`, `messages`, `unread`, `activity`, `thread`, `conversations`, `teams`, `people`, `calendar`, `calendar event`, `calendar actions`, `transcripts`, `transcripts show`, `transcripts fetch`, `transcripts signin`, `content fetch page`, `content fetch stream`, `content signin`, `content list`, `content search`, `content show`, `content sources`, `stores`, `records`, `sql`, `watch`, `skill`, `version`, `metadata`.

Out of scope: sending, reacting, marking read or any other write to Teams; using Teams tokens; classic Teams; Linux hosts (CI runs on Linux, but there is no Teams desktop cache to read there); downloading attachments or media (files and links are stored as metadata; transcript text is in scope); a terminal UI.

### Recovery command context

Concrete Loop source retry/compact-inspection commands, Office registry/OneDrive usage single-file retries, Outlook link fixes and calendar-event transcript-fetch follow-ups MUST retain the selected absolute archive and effective output format (`text`, `json` or `log`, including `--json` precedence). The route spellings below, such as `m365crawl docs sync --registry-file FILE`, name the operation: executable follow-ups include the archive/format globals, for example `m365crawl --db ARCHIVE --max-age 0 --format json docs sync --registry-file FILE`.

Archive-only inspection and projection MUST NOT acquire a native source. An ordinary sync offered to repair a selected source or apply a link MUST retain the selected Teams/Outlook roots, including Outlook `none`, and the exact link profile/principal; relative roots are resolved in the originating invocation's directory. An event transcript follow-up MUST retain the resolved Teams account and event target. Item-only `--fields` or flags incompatible with the destination MUST NOT be copied. Registered single-file sources retain their positive `--source-id`; never-admitted sources retain the exact explicit file selector, never an invented zero ID or combined selectors. Existing platform quoting, unsafe-Windows-locator refusal and unknown/null semantics are unchanged.

If the originating directory cannot be resolved for a relative archive or applicable acquisition root, recovery guidance MUST be explicitly non-executable and request an absolute `--db`, `--teams-root` or `--outlook-root` as appropriate; it MUST NOT silently emit the unresolved relative path as a replayable command. Archive-only follow-ups do not require acquisition-root resolution.

### Incomplete IndexedDB observations

A torn LevelDB journal is a partial observation, not evidence that an unseen record or database was removed. The readable prefix remains archivable and truncation remains a visible omission, even if no database name survived. Such observations MUST NOT introduce raw-record tombstones, false-gone calendar events, or advance calendar source freshness/day verification. A complete empty census remains authoritative; ordinary unreadable/bad-key databases retain their existing per-database failure semantics. Credential-denied and unsafely scrubbed data are still purged. Decoder/read-memory identities invalidate older successful fingerprints and digests when this contract changes.

### Interrupted and incomplete sync attempts

Cancellation after an Outlook calendar commit MUST preserve the committed calendar report and rows but return interruption, not covering success. Mail and link work must not be committed after the stop; a cleared mail-read marker permits the next ordinary attempt to finish the unread mail. Interruption before any committed source remains a failed attempt. Optional-source failures keep their existing semantics.

An unresolved report-significant Teams omission MUST be counted again on an identical subsequent sync: the source MUST NOT store a reusable successful fingerprint until a real read resolves the loss. Clean denial/redaction-only observations may still use the unchanged shortcut. A filtered read must not suppress a later unfiltered read. Outlook retains its separate persisted-omission contract.

## 2. Data sources and the credential denylist

New Teams runs an Edge WebView2 whose user data directory is `~/Library/Containers/com.microsoft.teams2/Data/Library/Application Support/Microsoft/MSTeams/EBWebView` on macOS and `%LOCALAPPDATA%\Packages\MSTeams_8wekyb3d8bbwe\LocalCache\Microsoft\MSTeams\EBWebView` on Windows (the default `--teams-root`). m365crawl reads that directory as follows.

- **Profiles.** Every `WV2Profile_*` directory (any directory under the root that has an `IndexedDB` subdirectory).
- **Origins.** In each profile, every directory `IndexedDB/https_teams.microsoft.com_<n>.indexeddb.leveldb` or `https_teams.cloud.microsoft_<n>.indexeddb.leveldb` (with its sibling `.indexeddb.blob` directory). One profile and origin pair is one **source**, identified as `<profile>|<origin>`. Other IndexedDB origins are never read; `status`, `sync` and `doctor` list their names (`other_origins`) so drift is visible.
- **Databases.** Inside an origin, database names follow `Teams:<manager>:react-web-client:<tenantId>:<userId or 8:orgid:userId>:<locale>`. The tenant and user ids of an account come from that name.

m365crawl reads every database in the origin except credential material. The rule is deny-only: a database or object store is read unless its name is denied, and the operator has ruled that agents get open access to all other Teams data.

**Typed databases.** These three have mappers and become the typed tables of section 3:

| Manager | Object store | Becomes |
| --- | --- | --- |
| `replychain-manager` | `replychains-2` | messages (each record is a reply chain holding a map of messages) and people |
| `conversation-manager` | `conversations` | conversations and people |
| `activity-manager` | `feed-items` | activity items |

A typed manager that is absent is skipped; one that is present without its object store fails the sync with `store_missing`.

**Generic databases.** Every object store that is not denied and not consumed by a typed mapper is read, record by record, into the `records` table (section 3.1) with the key and the value as canonical JSON. That is every store of every other database, plus the other stores of the three typed databases: only the exact `(manager, object store)` pairs in the table above are excluded, and a typed database whose only store is the typed one contributes nothing. This includes, on a real cache, pinned messages, contacts and call history until they get typed mappers. The read takes a census of the cache first (it knows each database's id, name and object store ids), groups databases in order into batches whose estimated memory is at most 64 MiB, and opens the cache once per batch with only that batch's kept object stores loaded: excluded and denied stores are never loaded into memory, and there is no second metadata pass. The census counts a whole database, so it can over-estimate a database with excluded stores; that only makes batches smaller. After each batch the heap is collected. A database larger than the budget is read alone. The peak is therefore about the larger of the budget and the largest single database's kept stores, plus the keys seen in the database being read: the set of keys seen is dropped as soon as that database has been compared with the archive (section 3.2), never accumulated over the whole read. A fatal error inside one database (not a cancellation) makes that database incomplete and counts one `database_unreadable` omission; the read continues with the next database, and a batch that cannot be opened does the same for every database in it. Sync and watch cost on a large real cache is not measured yet and is gated on a run on a work machine before release.

**The calendar is a projection of `records`.** Four of those object stores also feed the calendar tables (section 3.1): `calendar` and `calendar-internal-data` of `Teams:calendar:react-web-client:...`, `meetforwork-meeting-catch-up` of `Teams:meetforwork-manager:...` and `meeting-recap-catchup` of `Teams:meeting-recap-manager:...` (the list is `teamscal.ClaimedStores`; the `calendar-manager` / `events` store of the test fixture is not Teams' calendar and is not claimed). They stay in `records` and in `stores`: the calendar tables are derived from them (section 4, step 6), never a replacement. A recap record of `meeting-recap-catchup` is `{data, recapId, syncTimeUtc}` and its content (`callId`, summaries, `actionItems`, `atMentionEvents`, times) is under `data`; the mapper reads only that shape.

**The Outlook store (second source).** The new Outlook for Mac keeps its mail and calendar in `HxStore.hxd`, one per profile directory under `~/Library/Group Containers/UBF8T346G9.Office/Outlook/Outlook 15 Profiles` (the default `--outlook-root`; section 4.2 and `docs/outlook-store.md`). It is read when that directory exists and holds a profile, on macOS only. Besides the event and detail objects of the calendar, the account objects, which hold the addresses of the accounts signed in to the profile, are read, for one thing: the automatic link of section 4.2. Teams supplies the other half of that match: the record of the signed-in user in the `profiles` store of the account's own `Teams:profiles:` database, which is an ordinary generic record.

**Denylist.** A database name or an object store name is denied when, ignoring case, it starts with `Teams:auth` or contains one of `auth`, `token`, `credential`, `secret`, `cookie`, `msal`, `oneauth`, `key-store`, `keystore`, `keyval`, `session`, `key-value`, `keyring`, `crypto`, `encrypt`, `pkce`, `bearer`, `password`, `refresh` or `adal`, or has `aad`, `keys`, `jwt` or `e2ee` as a whole segment (delimited by the start or end of the name, one of `-`, `_`, `:`, `.` and `/`, or a camelCase boundary, so `userKeys` matches `keys` while `load` does not match `aad`). The list over-denies on purpose: a wrongly denied name costs one missing store, a decoded token costs a leaked credential. A denied database is never opened for values, walked, decoded, listed by name or logged; only its count appears, as the omission `denied_database` (and `denied_store` for a denied object store inside an allowed database). Adding a name to the denylist is a SPEC change; removing one needs the same review as adding a decoder. A name added to the denylist later is enforced on rows already archived: see "Credential purge" in section 3.2. Beyond names, values of allowed stores are scrubbed before they are archived (section 8).

## 3. The archive

The archive is one SQLite file (WAL mode) at `~/.m365crawl/m365crawl.db` on macOS and `%LOCALAPPDATA%\m365crawl\m365crawl.db` on Windows by default, overridable with `--db` or `M365CRAWL_DB`. A relative `--db` path is resolved against the current directory. On Windows the default path is private by construction: m365crawl creates the default directory boundary with a current-user + SYSTEM ACL before SQLite writes bytes. A custom `--db` path is allowed when its direct parent directory is already private enough or m365crawl can create that parent itself as a new private directory; if the direct parent already exists and is not private, or the archive file already exists and is not private, open fails with `db_error` before SQLite opens the database. The archive's schema version is 13 (`schema_migrations`, shown as `schema_version` by `status` and `doctor`). Legacy timestamps are UTC text with millisecond precision; optional knowledge/native observation clocks retain fixed-width nanosecond precision. Output is RFC3339 UTC.

Rows are partitioned by account: `(tenant_id, user_id)`. Two accounts never mix. The user id is the bare GUID; the account's own sender id is `8:orgid:<user_id>`.

#### Office registry variant

Schema 14 adds `variant` (default `office_json`) to document locator metadata, observations and capture metadata, and nullable `registry_json` and `opened_at` to `document_observations`. The change is additive: existing rows keep their IDs, payloads and full-text entries, and read as `office_json`. An Office registry source has knowledge kind and variant `office_registry`, an empty surface and the fixed application label `registry`; its observations store the complete native claim (`NodeID`, `ApplicationPath`, `ApplicationValue`, `Title`, `URL`, `FriendlyPath`, `OpenedRaw`, nullable `Size` and `Pinned`) in `registry_json` and never an Office JSON document. Every read and admission MUST validate variant, kind, label and payload together; a mismatch is an error, not an empty result. A representation is the full native claim plus its source binding and qualification `office-registry-v1/mapper-v1`; a repeated one keeps its original clocks, and the same claim in two sources is two representations.

The registry input is a SQLite file Office writes: `~/Library/Group Containers/UBF8T346G9.Office/MicrosoftRegistrationDB/MicrosoftRegistrationDB_*.reg` by default on Mac (at most 16 matched files among at most 4096 directory entries), or one file given with `docs sync --registry-file FILE` on Mac or Windows; there is no default discovery on Windows or Linux. On Windows the supplied path MUST match each directory entry's exact long name and letter case, and each ancestor directory is enumerated on every validation and refused above 4096 entries or 1 MiB of names; these refusals are `office_registry_input_unqualified`. `--root`, `--registry-file` and `--source-id` are mutually exclusive: `--root` is JSON-only and `--registry-file` is registry-only. A default explicit sync MUST try the JSON and registry families independently; a family that is absent or refused is a `discovery` outcome `{kind, code, meaning}` with a fixed code and no source ID, and MUST NOT suppress the other family or any registered source. When at least one family was usable or at least one registered source was attempted, the command exits 0 and reports the other family under `discovery`. When neither family was usable and no registered source was attempted, nothing was read: the command MUST fail with exit 3 and the Office JSON family's code, as it did before the registry family existed, naming both family codes in its message. Cancellation and archive errors remain command errors. A supplied `--registry-file` that does not exist, is not a regular file, or is the archive database or one of its own files (`-wal`, `-shm`, `-journal`, `.lock`) is a usage error that registers nothing; this check reads directory metadata only and MUST NOT open the archive as a source, because closing such a descriptor would release the process's own locks on the archive. Only a file that was opened and then refused is registered as a failed source. No command removes a source: a failed source stays listed until a later sync of it succeeds.

Registry acquisition MUST apply the same positive local admission as Office JSON, limits the input to 64 MiB inclusive. The header and the companion metadata are first read through the held descriptor without a lock; SQLite SHARED protection is then taken, and the same header and companion state are read again under it and MUST equal the first reading before any byte is copied. The protection MUST be held from that point until the private copy is validated and removed, and MUST be released, with the source descriptor closed, on every return path including failure and panic. One process-wide source-descriptor gate serializes notes, Office JSON and registry discovery, observation and capture, because closing any descriptor of a file releases the process's record locks on it; the archive lock is taken before that gate and the gate before the SQLite byte locks, and no second descriptor of the source is opened while the protection is held. Validation while protected uses the held descriptors and held-parent name lookups only. A source with a write lock or a non-empty rollback journal is `office_registry_source_busy`, and stays so while the journal remains: the capture never replays or removes a journal; a non-empty write-ahead log, any shared-memory file, a link, more than one hard link, a header that is not SQLite in rollback-journal format or an unqualified path is `office_registry_input_unqualified`. The result is staged inside the capture and committed only after late validation, private-copy removal, unlock, source close and policy restoration all succeeded. Per-source reasons are `office_registry_input_unqualified`, `office_registry_source_busy`, `office_registry_index_unreadable`, `office_registry_index_too_large`, `office_registry_index_unrecognized`, `office_registry_capture_failed`, `office_registry_cleanup_failed`, `office_registry_policy_restore_failed` and `office_registry_cancelled`. Entries that cannot be mapped are counted under loss `office_registry_document_unmapped` (coverage partial); a list with no documents is complete with reason `office_registry_listed_no_documents`.

A locator whose first capture failed has no admitted source: its coverage row has `source_id` null and its `fix` MUST name `m365crawl docs sync --registry-file` with the file path, never `--source-id 0`. The path MUST be quoted for the platform the source was registered on so that pasting the command cannot run text from the file name: POSIX single quotes elsewhere than Windows; on Windows double quotes, and a name with a character that cmd.exe or PowerShell expands inside double quotes (`$`, backtick, `%`, `'`, `&`, `^`, `!`) is not interpolated and the fix refers to the `locator` field instead. After an admitted capture the retry names `--source-id N`.

Registry output adds `variant`, `registry_native` and `opened_at` to the document item and omits `native`; an Office JSON item has none of the three, so its bytes are unchanged. `opened_at` is `OpenedRaw` parsed to UTC only when it is RFC 3339 with an explicit `Z` or numeric offset and at most nine fractional digits; otherwise it is null and the raw text stays in `registry_native.OpenedRaw`. It MUST NOT fall back to host locale, file time or capture time. The registry states no modification time: `modified_at` is null, date windows exclude registry rows, and they sort with unknown times. There is no opened-time filter. `docs list --order-by opened_at` orders rows with a non-null `opened_at` first, newest first, and the rest in the default order after them; `--order-by modified_at` is the default order, and any other value is a usage error. `docs search` and shared `search` take no order flag. When a date window is set, `docs list`, `docs search` and shared `search` MUST add one `notices` sentence that gives the exact number of rows the window left out because `modified_at` is null and that otherwise matched every other filter, by kind (Office JSON, Office registry, OneDrive usage recent, document, collaborator) with the reason; no sentence is added when the number is zero. Text `docs list` prints one line naming `--order-by opened_at` when the default order returned rows and none has a `modified_at`. Text lists show the opened time in its own `opened_at` column and never under `modified_at`. `--application registry` selects registry rows and `--surface` never matches them. `--max-text` clips `Title`, `FriendlyPath`, `ApplicationPath` and `ApplicationValue` only. Metadata search indexes the title, URL, friendly path, application claims and node ID. References are the exact URL and the literal friendly path, unresolved; neither is ever opened, stat'ed or resolved.

#### OneDrive usage variant

Schema 15 adds nullable `usage_json` and `native_key` (default empty) to `document_observations`, nullable `members_capture` to `document_capture_metadata`, and the table `document_usage_relations(capture_id, recent_rowid, document_rowid)`. The change is additive: existing rows keep their IDs, payloads, full-text entries and order. An archive at schema 14 or older that is opened read-only (`--max-age 0`, `docs sources`) is read without these columns, has no usage rows and MUST NOT be migrated. Every command that opens the archive for writing migrates it: any sync, and any read that refreshes first. After that an older m365crawl refuses it with `archive_newer`.

Usage availability is independent of the optional membership pointer. A pre-pointer schema-15 archive with usage payloads and copied unchanged captures MUST remain readable without migration: when `members_capture` is absent, capture C owns its own members and relations; when present but null, the same rule applies. Archive-only snapshot, detail and relation reads MUST preserve the main file and physical schema. For compatibility, `native_key` retains its original delimiter encoding as a payload check, not a unique tuple or ordering encoding. Duplicate identity MUST compare the literal `(Type, ID, Format)` components without collisions, and ordering MUST compare those full components separately before limits or output clipping; admitted components may contain the legacy delimiter. Existing native keys and observation IDs are not rewritten.

Membership is stored once, for every document family. A capture that changed the source writes its own `document_capture_members` rows and has `members_capture` null. A capture admitted as `unchanged` MUST write no member row and no relation row: its `members_capture` names the capture that owns its predecessor's rows (`coalesce(previous.members_capture, previous.capture_id)`), and it MUST carry no observations and no losses of its own. The frontier, the last-good capture, `admitted_at`, retained state and stale-attempt refusal are unchanged by this, and no earlier row is rewritten. A capture from before schema 15 that copied its predecessor's rows has `members_capture` null and stays valid. Every reader MUST resolve the owner before joining; in raw SQL the rows of capture C are `select observation_id from document_capture_members where capture_id = (select coalesce(members_capture, capture_id) from document_capture_metadata where capture_id = C)`, and `document_usage_relations` is keyed by the same owner. `sql --help` states this. A OneDrive usage source has knowledge kind and variant `onedrive_usage`, an empty surface, the fixed application label `onedrive` and qualification `onedrive-usage-v1/mapper-v1`. Each observation stores one complete native record in `usage_json` as `{Type, Document | Recent | Collaborator}`: `Type` is `recent`, `document` or `collaborator` and exactly the payload it names is present. Native identity within a source is `Type` plus `ID`, and for a document also `Format`; `native_key` holds it. Every recent row is its own observation whether or not formatted variants exist, every formatted variant is its own observation, and no variant is preferred or merged. A representation is the full native record plus its source binding and qualification; a repeated one keeps its original capture and clocks, a changed one is a new observation, and the same record in two sources is two representations. Every read and admission MUST validate variant, kind, label, payload, native key and modification time together; a mismatch, an unknown payload field or a relation to a missing or mistyped observation is an error, not an empty result. No person, alias, people observation, conversation or account is created or linked from a usage record.

`document_usage_relations` holds, for each admitted capture, one edge from each recent row to every document row of that capture with the same native ID. Edges are stored under the capture that owns the membership: a capture that changed the source has its own, an unchanged capture shares its owner's and adds none, and earlier edges are never rewritten. `docs show` reads a usage row's relations from the membership owner of the source's admitted capture when the row is a member of it, otherwise from the last owning capture that held the row, in the same snapshot as the row, and returns the first 100 in native-key order with the exact total; `usage_relations.capture_id` is that owning capture.

The usage input is a SQLite file OneDrive writes: `~/Library/Application Support/OneDrive/settings/ListSync/Business_<GUID>/Microsoft.FileUsageSync.db` by default on Mac (the exact leaf of at most 16 account directories among at most 4096 entries per directory), or one file given with `docs sync --onedrive-usage-file FILE` on Mac or Windows. There is no default discovery on Windows or Linux, and no OneDrive library or sync database is read. A directory name is a local name only: it is never used as an account, tenant or person identity. `--root`, `--registry-file`, `--onedrive-usage-file` and `--source-id` are mutually exclusive, and `--onedrive-usage-file` reads only that file. A default explicit sync MUST try the usage family independently of the JSON and registry families. Its family outcomes are `onedrive_usage_unavailable` (no settings folder, or no account folder with a usage file), `onedrive_usage_default_unsupported` (a platform with no default location) and `onedrive_usage_input_unqualified` (an unsafe folder or leaf, or more entries or accounts than the limits; the whole family is refused). Its located outcomes carry `locator`: `onedrive_usage_discovery_unsupported` for a `Business_` or `Personal_` directory whose name is not `Business_` plus a GUID, and `onedrive_usage_unavailable` for an admitted account directory without the leaf. The exit rule of the registry variant applies to three families: exit 3 with the Office JSON family's code only when no family was usable and no registered source was attempted. A supplied file that is missing, not a regular file, or the archive database or one of its own files is a usage error (exit 2) that registers nothing.

Usage acquisition is the registry's: the same positive local admission, source-descriptor gate, lock order, SQLite SHARED protection, private copy, late validation and cleanup, with a 512 MiB inclusive input limit and one 30-second deadline that starts before the wait for the gate. The reader's limits are unchanged: 1 MiB per field, 64 MiB of retained strings, 65536 recent rows, 65536 documents, 4096 collaborators and 262144 history instances and participants in total. A write-ahead log or shared-memory file beside the source is `onedrive_usage_input_unqualified`; the capture MUST NOT consolidate, checkpoint or copy a write-ahead log. A database in write-ahead mode is refused on every attempt, and the `fix` MUST say so rather than advise a retry. A write lock or a non-empty rollback journal is `onedrive_usage_source_busy`. The result is staged inside the capture and committed only after its late validation, private-copy removal, unlock, source close and policy restoration succeeded. The fixed failure reasons are `onedrive_usage_input_unqualified`, `onedrive_usage_source_busy`, `onedrive_usage_index_unreadable`, `onedrive_usage_index_too_large`, `onedrive_usage_index_unrecognized`, `onedrive_usage_capture_failed`, `onedrive_usage_cleanup_failed`, `onedrive_usage_policy_restore_failed` and `onedrive_usage_cancelled`. Rows that cannot be mapped are counted, not kept, under the losses `onedrive_usage_recent_unmapped`, `onedrive_usage_document_unmapped`, `onedrive_usage_document_orphan` (a formatted row whose native ID has no recent row) and `onedrive_usage_collaborator_unmapped`; any loss makes the capture partial. A complete capture with no row has reason `onedrive_usage_listed_nothing`: it supersedes current membership and keeps earlier observations as retained. A locator whose first capture failed has `source_id` null and its `fix` MUST name `m365crawl docs sync --onedrive-usage-file` with the path quoted by the registry's rules, never `--source-id 0`.

Usage output adds `variant`, `usage_native` and `full_inspection` to the document item and omits `native`; Office JSON and registry items are unchanged. `title` and `url` are a document record's own and empty for recent and collaborator records; they MUST NOT be invented. Every native clock is `{Raw, Value}`: `Value` is `Raw` parsed to UTC only when it is RFC 3339 with an explicit `Z` or numeric offset and at most nine fractional digits, otherwise null, and it MUST NOT fall back to host locale, file time or capture time. `modified_at` is `Document.Modified` or `Recent.FileModified` only; access, sharing, saved, row-change and capture times never satisfy a date window, and a collaborator's `modified_at` is null. A clock written without a zone (the form `YYYY-MM-DD HH:MM:SS`, which every recent-row clock had in the OneDrive files examined) therefore has a null `Value`: a recent row's `modified_at` is then null, a date window never returns it, and its access clock is not an ordering key. Lists keep the existing order and break ties, after source ID, by native `Type`, `ID` and `Format` before observation ID. `usage_native.Document.History` previews the first 100 instances in native order with `Position`, and each instance and `Latest` previews its first 100 participant rows, repeats included; `HistoryCaptured`, `ParticipantsCaptured`, the `*Truncated` flags and `PreviewTruncated` are exact, and `ParticipantsCount` is the file's own stated number or null. A collaborator's `Emails` are previewed the same way. `--max-text` clips descriptive names, titles and subjects only, never a native ID, URL, address, thread ID or `Raw` clock. `full_inspection` is a fixed archive-only `sql` command around the positive observation row ID and the archive path; it MUST NOT contain source text. Metadata search indexes a document's title, URL, extension, owner and native IDs, the names, addresses, subjects and thread IDs of all its sharing claims and participants, a recent row's native IDs and extension, and a collaborator's stated profile; it indexes no other string of the usage file. A document's reference is its exact URL, unresolved. `--application onedrive` selects usage rows and `--surface` never matches them. Sharing names, addresses, thread and meeting IDs and collaborator profiles are source claims: output MUST NOT emit a thread, chat, mail or person follow-up command or an alias for them, including when a value equals an archived identity, and account, author and message-only filters MUST NOT select usage rows.

### 3.0.3 Teams message application evidence

Schema 12 adds `messages.raw_digest` (the 32-byte SHA-256 of the archived native JSON as a blob, NULL when it is absent; representations and output carry it as lowercase hex), immutable `message_app_observations` and the pointer table `message_app_current`. A representation is keyed by the complete message key, `sender_id`, `raw_present`, `raw_digest` and `mapper_version`, holds `state` (`mapped`, `partial`, `failed`, `absent`), `failure_code` and the bounded `projection_json` (app id and name, native reply-to id, admitted citations with decimal-string ids, losses), and is never rewritten. `message_app_current` names each message's `current_id` and `last_good_id`, keyed by the message's `rowid` (`message_rowid`; messages are never deleted and the archive is never vacuumed). The pointers are not declared foreign keys; a read reports a dangling or inconsistent pointer as `teams_app_projection_corrupt`. Mapper version 2 decodes a JSON-string `properties.botMetadata` (its native encoding) with the same strict parser and the record's shared depth and member budget, starting at the container's depth; exactly one object is mapped like a native object, any other content stays one `teams_bot_metadata_unmapped` loss, and budget exhaustion inside it is the record's `teams_app_raw_too_large`. No other string property is reinterpreted.

- Publication happens in the transaction that accepts a message insert or update, so a rolled-back source leaves no evidence. Mapped representations, and partial ones with admitted claims, become last good; an absent one clears last good; failed ones, and partial ones without claims, keep it.
- A writable `sync` backfills offline, before any capture, when `meta.message_app_mapper_version` is lower than the active mapper version (or unreadable); an older binary on a newer archive neither reprocesses nor rewrites it: it fills `raw_digest` and the pointers without changing message content, hashes, text, index, update clocks or legacy counts, and writes the marker with the complete transaction. Reads with `--max-age 0`, and read-only older archives, never derive evidence: they report `not_derived`.
- Reads select messages and load their evidence in one read snapshot. A current representation that does not match the message as archived now is `not_derived`; a dangling or inconsistent pointer or a representation that fails validation is `failed` with `teams_app_projection_corrupt` and no payload; a failed current serves a validated last good representation as retained with reason `current_failed`.

### 3.0.4 Cached Loop channel observations

Schema 13 adds `loop_locator_metadata`, `loop_attempt_evidence`, immutable `loop_snapshots`, `loop_snapshot_losses` and `loop_channels`, and stable-rowid `loop_fts(path, text)`. All are additive and derived only from `records` rows with database `fluidDriverCache` and store `driverStorage.V3`; no cache file, network service, browser or Loop component is read, and `records` is never changed. A registration is the exact archived tuple (`source`, `database`, `store`, `key_json`), registered as an `archive` platform `loop_cache` knowledge locator before any value is read, so a failed, refused or metadata-only tuple keeps a stable `source_id`. Identity bounds are 4 KiB source, 64-byte database and store names, 256 KiB key and 4 KiB per owner ID, all valid UTF-8; a value larger than 8 MiB is refused before it is loaded.

- Discovery never blocks. An explicit run without `--source-id` scans unregistered records in numeric `records` rowid order, reading identity fields only (lengths are checked in SQL before a field is loaded). It registers and projects at most 128 identity-valid tuples per run: each is registered, then its one value is loaded, parsed, committed and released before the next is read. A record with an invalid identity is never registered and does not count toward the 128; the report counts them (`invalid_records`) and names the first 16 by rowid in `diagnostics`, never by an archived string. When unregistered records remain past the batch the report has `discovery_remaining` true, `discovery_remaining_records` and a `notice` to run `m365crawl loop sync` again, and the run exits 0. A run that fails after it wrote reports what it committed on stdout and the error on stderr.
- Owner IDs shown as `current_tenant_id` and `current_user_id` come only from an identity that passed those bounds. A registered record whose identity no longer does has empty current owner IDs and reason `loop_cache_identity_unqualified`, and a refresh records that failure and keeps the last good snapshot.
- Each admission stores the archived record's fingerprint (`content_hash`, value length, update clock, raw digest, redaction state) in `loop_attempt_evidence`. A read compares that fingerprint first and loads and hashes the value only when it differs or none is stored, so an unchanged source costs no value load; a source with no admitted snapshot is never loaded on a read. An ordinary read decides whether a refresh is due from attempt times alone and reads the sources once, in the same read snapshot as its rows. `--source-id` selects its one registration in the query.

- A snapshot is keyed by registration, exact value digest and reader qualification (`loop-cache-v1/mapper-v1`); the same digest and qualification reuses it with its original clocks, and a new qualification projects a new snapshot from the same bytes. Snapshots, losses and channels are never rewritten or deleted. Each channel (`loop-channel:<rowid>`) holds its path, native signed 64-bit sequence, partial text, marker and pending-operation counts.
- Publication rechecks, inside its transaction, that the archived record still has the attempt's exact value, owner IDs, update clock, removal state, raw digest and redaction state; any change records `loop_cache_input_changed` and publishes nothing. A stale attempt never overwrites a newer one. Failures carry exactly the reasons in docs/commands.md (`loop sources`) and keep the last good snapshot current.
- A snapshot with channels has coverage `channels` (or `partial` with losses or pending state); one with none is `metadata_only` with reason `loop_cache_metadata_only`. Status is `complete` or `partial`; neither claims a full, current or server-complete page.
- Reads resolve rows, sources and `snapshot_match` (`no_admission`, `matches`, `differs`, `unavailable`) in one read snapshot. `matches_retained_value` compares the archived record's current bytes and reader qualification with the snapshot's, through that fingerprint: a change made outside m365crawl that leaves `content_hash` unchanged is not detected; `retained` means a newer admitted snapshot exists. `modified_at` is always null; `record_updated_at_at_admission`, `projected_at` and the raw clocks are never native edit times. Association state is `unresolved`; owner IDs are archived evidence, not a resolved account.
- Explicit `loop sync` registers and projects. Ordinary Loop reads and participating shared search refresh only registered sources whose last attempt is older than `--max-age`; `--max-age 0`, `loop sources` and a missing archive never lock, migrate, create or write. `loop show` resolves the stored channel before refreshing only its source and returns the same immutable channel. A failed refresh serves the retained archive with `refresh_error`; cancellation is the command's error.
- `loop_coverage` survives `--fields`, `--limit` clipping and zero hits. Its `state` is `not_registered` or `registered`, and `totals` counts the participating sources (`registered`, `failed`, `metadata_only`, and `matches`, `differs`, `unavailable`, `no_admission`). Loop commands list every source in full. Shared search lists each source as `{"source_id", "state", "snapshot_match", "raw_present", "reason", "inspect"}` only, where `inspect` is the `loop sources --source-id N` command; it never carries the tuple. Shared search refreshes Loop after the implicit sync. Unconstrained shared search includes Loop channels after every dated hit and never advertises a chat-only total; date, account, author, chat-only, mail-only and profile filters exclude Loop from `all` with a notice and are `flag_source_conflict` with `--source loop`. Loop commands refuse `--account`, `--outlook-account` and `--outlook-profile`.

### 3.2 Archive semantics

- **The archive outlives Teams' cache.** Teams evicts old messages from its own cache as it runs. m365crawl MUST NOT delete a message, conversation, person or activity item because it disappeared from the cache. No code path issues a `DELETE` against these tables (it only replaces the full-text rows of a row it updates).
- **Deletions are tombstones.** When Teams marks a message deleted, the row gets `deleted_at`. The row, its text and its `raw_json` remain.
- **`deleted_at` is sticky.** Once set, it stays set when a later sync sees the same or an older version of the message without it. A strictly newer version without a deletion clears it.
- **`--include-deleted` is off by default.** `messages`, `search` and `thread` hide deleted messages unless the flag is given. Deleted messages are never counted as unread.
- **Idempotent upserts.** A message changes only when the incoming `version` is newer, or the version is equal and the content hash differs. An older version is ignored. A second sync with no new Teams activity changes no row.
- **Unread** means: the message is newer than its conversation's `read_horizon_at`, is not deleted and was not sent by the account's own user. The horizon comes from Teams' consumption horizon in the conversation properties.
- **`mentions_me`** is true when the message mentions the account's own user by id, or the account's activity feed holds a `mention` or `mentionInChat` item for it (which covers channel, team, tag and @everyone mentions). **`mention_kind`** says which, computed at query time: `person` when the mention is by id or the feed item's subtype is `person`; otherwise the feed item's subtype (`channel`, `team`, `tag`, `everyone`), or `other` for a subtype this version does not know. A message that does not mention the account has none. A direct mention is `mention_kind` `person`.
- **System pseudo-conversations** `48:notifications`, `48:calllogs` and `48:annotations` are hidden from every list command unless `--include-system` is given, because they duplicate real messages without sender or conversation names. `48:notes` (the user's own notes) is not hidden.
- **Derivation version.** Text, sender names and untitled-chat names are derived from `raw_json` by the mappers. The archive records the mapper generation in `meta.derivation_version`; this build writes 2. An archive with no such row was written by alpha.1 (version 1). The first `sync` on an older archive recomputes the derived fields of every stored row from its `raw_json` (rows Teams has since evicted included), rebuilds their text indexes, and records the new version, all in one transaction before the cache is read. The recomputation counts as no update and no edit. An archive with a higher derivation version than the build's is refused with `archive_newer` before any write.

- **`records` follow the same rules.** A record that leaves the cache gets `removed_at` (a sticky timestamp) and keeps its last value; it is never deleted (the credential purge below is the one exception). This holds for one record gone from a store that was read completely, and for a whole database that is no longer in the origin (a filtered `--account` sync only marks that account's databases). A database read incompletely (a bad key, a `database_unreadable` failure, or a failure that fails the source) marks nothing. A record seen again clears `removed_at`. A record whose value cannot be decoded is stored with a NULL `value_json` the first time, and never overwrites a value stored earlier. A row changes only when its value's content hash changes. `updated_at` moves only then, or when a removed row returns.
- **Credential purge: the one exception.** Each sync, rows of the source whose database or object store name now matches the denylist get `value_json` NULL, `content_hash` empty and (when not already set) `removed_at`. This is the single case where the archive clears content it holds: credential material is cleared, not kept. The key stays. Rows already cleared are left alone.
- **Schema version.** A version 2 archive gains the `records` table in place when it is opened for writing, and its other rows are untouched. A version 3 archive gains the read-memory columns of `records` and the `typed_memo` table the same way (migration 4); its rows carry no memory yet, so the first sync after the upgrade reads every record in full. An archive whose schema version is higher than this build's is refused with `archive_newer`, by read commands too (`doctor` reports it as a failing check); builds before this one report that as a generic `db_error` instead.

- **The calendar tables follow the same rules, and keep the richest copy.** No code path deletes a calendar row. An event the cache stops holding is not deleted: it gets `removed_at` only when the cache still holds the event's day (the event was deleted, cancelled or declined away); an event whose whole day left the cache was evicted, and stays live. Teams fetches an event's attendees, body and rooms only for events the user opened, so a later, thinner copy never erases them: each unit of an event is compared against its own clock, a newer copy replaces it, an older or empty one does not, and where two copies are equally old the larger list wins (so an attendee removed at the same modification time can linger; `detail_as_of` says how old the detail is). A recap field group that arrives empty never replaces a stored one, and a recap item that a newer copy no longer lists gets `superseded_at` (a sticky tombstone), not a delete. The calendar tables hold attendee addresses and recap text, which are in the archive because they were in the cache.
- **Backfill and re-derivation.** The calendar is derived from `records`, which the sync keeps complete, so an archive upgraded from schema 4 fills its calendar on its first sync from the rows it already holds, without the Teams cache. `meta.calendar_derivation` holds the stamp `mapper=<teamscal.MapperVersion>;zone=<January and July UTC offsets of the sync zone, in seconds>;rules=<teamsdesktop.RulesStamp>`. A different mapper version maps every record again and captures it over what is stored. A different zone (covered days are taken in `time.Local` and never shrink, so days taken in the old zone would mix with the new) forgets the covered days and takes them again, from removed records as well as live ones, so a day whose events were evicted stays covered. A current stamp over empty calendar tables while calendar records exist (the tables were lost, the stamp was not) derives again. Different scrub rules (the stamp covers every rule table, and `teamsdesktop.RulesVersion` covers the code that applies them) additionally blank the content of every derived row first and rebuild what the records still back, so a copy made under an older rule does not outlive it; recap items that were blanked are marked superseded. The rebuild runs inside one transaction before any source is read.

### 3.3 Full-text index

`message_fts(message_key unindexed, content)` and `conversation_fts(conversation_id unindexed, title)` are FTS5 tables whose rowid equals the rowid of the owning `messages` or `conversations` row. The store maintains them in the same transaction as the upsert. `messages` and `conversations` are therefore rowid tables with no explicit integer primary key, and their rowids are load-bearing: an operation that renumbers them, such as `VACUUM` (SQLite documents that VACUUM may change the rowids of such tables), would silently detach the indexes from their rows. Nothing in m365crawl runs `VACUUM`, and nothing outside m365crawl SHOULD run it on an archive. If an archive's indexes are damaged, move it aside and run `m365crawl sync` to rebuild a fresh archive from the cache.

`transcript_fts(speaker, text)` indexes transcript entries the same way, by the rowid of their `transcript_entries` row, written in the transaction that stores a fetched part; `search` matches its `text` column only.

A `search` query is split on whitespace into terms that are ANDed. The same query language, built by one function, applies to chats, mail and transcripts, so a query with a syntax error is one usage error. `"quoted phrases"` match as phrases and a trailing `*` on a bare term is a prefix. Every FTS5 operator in the input is quoted, so it is an ordinary word.

## 4. Sync

`sync` mirrors every source into the archive once. A run proceeds as follows.

1. **Lock.** The run takes an exclusive, non-blocking lock on `<db>.lock` (a mode-0600 file on macOS, a current-user + SYSTEM protected file on Windows). The implementation uses `flock` on Unix and `LockFileEx` on Windows. If another sync or watch sync holds it, the run fails at once with `locked` (exit 4); it never waits. Read commands do not take the lock and work beside a writer.
2. **Sweep.** A `m365crawl-snapshot-*` temp directory older than one hour is removed only when its protected version-1 `.m365crawl-owner.json` names a positively dead creator PID. Teams and Outlook register exclusively before copying source files; the marker contains only version and PID. Registration failure removes only the newly allocated root and fails capture. Root and marker must be real, same-user private filesystem objects; root identity is rechecked immediately before recursive reclamation. An alive or reused PID, permission/query/close error, invalid metadata, symlink, foreign/unprotected object or missing/legacy marker retains the root. An executing owner's PID is retained without a process probe. Unix requires positive `ESRCH`; Windows requires a successfully queried terminated process handle, not an `OpenProcess` error. Uncertain Windows ACL or process evidence does not grant reclamation, so some abandoned roots remain. This does not register other callers of the shared private-root primitive automatically.
3. **Migrate.** An older archive is re-derived as described in section 3.2, and the calendar tables are filled or rebuilt from `records` when the archive has none yet or was derived by another mapper or under other scrub rules (section 3.2, "Backfill and re-derivation"; this needs nothing from the Teams cache). An archive that is newer than this build fails with `archive_newer`, and nothing is written, not even a failed-run record.
4. **Discover** the sources (section 2). Errors: `teams_not_installed`, `no_full_disk_access`, `no_teams_origin`.
5. **Per source:** fingerprint, skip or snapshot, decode, map, write.
   - The **fingerprint** is a SHA-256 over the decoder version and the sorted name, size and modification time of every file in the origin's `.leveldb` and `.blob` directories, excluding `LOCK` and `LOG*`. If it equals the fingerprint of the last successful run for that source, the source is `unchanged`, nothing is decoded and no row changes, unless the read is forced with `--full-read` (section 4.1), which does not stop at the fingerprint. A run with `--account` records no fingerprint and never skips, so a filtered run cannot hide another account's data from a later run.
   - The **snapshot** copies the two directories into a private temp directory (mode 0700, files 0600), regular files only. LevelDB data files are copied first, then the `MANIFEST`, then `CURRENT`; blobs last. The copy is retried, up to three attempts, when `CURRENT` changed during the copy, the copied manifest is not the size of the live one, or a file the manifest names is missing. After three attempts the run fails with `snapshot_inconsistent`. The snapshot is validated by reading every table and log. It contains Teams' sign-in database, so it is removed when the source is done, on failure, and on SIGINT or SIGTERM.
   - The **snapshot** copies the two directories into a private temp directory (mode 0700 with mode-0600 files on macOS, current-user + SYSTEM ACLs on Windows), regular files only. LevelDB data files are copied first, then the `MANIFEST`, then `CURRENT`; blobs last. The copy is retried, up to three attempts, when `CURRENT` changed during the copy, the copied manifest is not the size of the live one, or a file the manifest names is missing. After three attempts the run fails with `snapshot_inconsistent`. The snapshot is validated by reading every table and log. It contains Teams' sign-in database, so it is removed when the source is done, on failure, and on SIGINT or SIGTERM.
   - **Decode and map** read the typed stores of the snapshot, then every other database that is not denied (section 2). A record whose stored bytes have not changed since the last committed sync is skipped, not decoded (section 4.1).
6. **Write.** Each source is applied in **one write transaction**: accounts, conversations, messages, activity items, people, generic `records`, the calendar tables derived from them (below) and the source's `sync_runs` row commit together or not at all. Records are applied in batches of 2,000 (or about 4 MiB of values) so memory stays bounded. Right after each generic database is read, its rows that are no longer present get `removed_at` when it was read completely, and the keys seen are dropped; after the last one, rows of databases the origin no longer holds get `removed_at` too, and rows under a name the denylist now matches are cleared (section 3.2). People are merged across the whole source; the newest sighting names a person. Sources are independent: a source that fails (including from a panic, which becomes `internal`) rolls back completely, is recorded as `failed`, and does not stop the sources after it. Sources that committed stay committed.
   - **Derive the calendar** (the last write of the source's transaction, after its records are written and before it commits). `DeriveCalendar` maps only the calendar and recap rows this sync inserted or changed (`records.updated_at` at or after the sync's start); with skipping (section 4.1) an unchanged record is not rewritten, so it is not mapped again. The days the cache holds now are read from every live calendar record by SQL (the start time and event type only, in the machine's zone), upserted into `calendar_covered_days`, and the window is the span of every covered day ever seen, so neither shrinks. A removed calendar record whose day is held now marks its event gone (`removed_at`, all data kept) only when no source that holds the account has the event live (two Teams profiles can hold one account, and an event keyed by account and source id is one event); one whose day is not held is eviction. A record that reappears clears it. Only an account whose cache this sync read (it found one of that account's databases) gets a fresh window, `synced_at` and covered-day `last_verified_at`: a sync of one account, or of a source that no longer holds another account, leaves that account's freshness as it was; a rebuild from the records reads no cache, so it keeps `synced_at` and re-verifies no known day. A record that cannot be mapped is the omission `calendar_unmapped` (a loss: it makes the sync `ok_with_omissions`); an event the core refuses is `calendar_refused` (also a loss). Both are counted on every sync, not only on the one that rewrites the record: the derivation keeps what it could not use in `calendar_losses` (per record, with a reason that names a field or a shape and never content), replaces a record's entries whenever it maps the record again, ignores a removed record, and reports what still stands for the accounts it read. A sync that finds the cache unchanged reads nothing, and still reports the stored losses of its source, so it is `ok_with_omissions` and not `unchanged` while data is missing (so is the run that upgraded the calendar); an event in a time-zone name m365crawl does not know is stored and shown, `time_zone_iana` empty, and counted as `calendar_unknown_time_zone`; an all-day event whose times fit no whole-day shape is stored as timed and counted as `calendar_all_day_unaligned`. The last two are not losses. Recaps without an `ical_uid` are then linked to the one event whose start and end are within `teamscal.RecapTimeTolerance` (link method `time`), and those still unlinked to the one live, timed, non-master event that is neither cancelled nor declined and starts within five minutes of the recap's meeting start (`calendar.RecapStartTolerance`, link method `start_time`), because a recap's end is when the call ended, not the scheduled end. A start link is recomputed on every derivation: all `start_time` links of the account are cleared first and made again from the events as they are, so the result does not depend on the order rows arrived in, and a link that is no longer unique or whose event went is dropped. A link by id (`ical_uid`) or by both times is never touched, and an id that arrives later replaces a start link. Zero candidates or several leave the recap unlinked, never guessed. A link by id is placed at read time: when several live occurrences share the recap's `ical_uid` (a series id), the recap belongs to the one whose start is nearest its `meeting_start` within `calendar.RecapStartTolerance`, and a recap no occurrence matches stays on all of them as a series-level link (section 6). `linked_by_start`, `unlinked_no_event` and `unlinked_ambiguous` are a census of the account's recaps after the derivation (those with a meeting start and no id), not what the run changed. The derivation runs in a savepoint: a failure of a calendar write rolls back only the calendar, is counted as the omission `calendar_derivation_failed` (a loss), and does not fail the source, whose messages and records commit; the stamp `meta.calendar_derivation` is then dropped so the next run derives the whole calendar again from `records`.
7. **Record and report.** The run writes its run-level `sync_runs` row (section 3.1) and prints its report (section 5, `sync`). Only a run in which every source succeeded counts as a fresh sync, for every account (or for the one account of `sync --account`). A partial or failed run refreshes no account.

### 4.1 Skipping unchanged records

A sync of a changed cache does work in proportion to what changed, plus one cheap pass over the raw cache. The result is always exactly what reading every record in full gives: the same rows, the same `seen`/`inserted`/`updated`/`unchanged` counts, omissions and `redacted` count, the same changes for `watch`, the same `removed_at` marks and the same people.

- **What is remembered.** For each record a sync read in full and mapped cleanly, the archive keeps a 16-byte digest of the record's payload (the V8 bytes after the Blink envelope, snappy and any blob file are unwrapped, so a blob-backed value is covered by what the blob holds) taken under a signature, and what the record did. A generic record keeps its digest and its redaction count on its own `records` row (`raw_digest`, `value_redacted`). A typed record (reply chain, conversation, activity item) keeps its digest and its effects in `typed_memo`: the rows it produced, each with the content hash the row held afterwards, and the people it named with their sighting times. It is written in the same transaction as the rows, so a rollback or a crash forgets it with them.
- **The signature** covers `DecoderVersion`, the derivation version and every rule table of the scrub and the denylist: the secret key names, the regular expressions, the depth limit, the sibling-field names, the replacement text, and the deny prefixes, terms and tokens. They all live in one registry (`ruleSet` in `internal/teamsdesktop/rules.go`) that `Scrub` and `Denied` read and that the signature hashes field by field, so adding a key name, a pattern or a term changes every digest without anyone having to remember to say so, and a test fails if a rule table is declared outside the registry. Anything that changes how bytes become rows therefore changes every digest, and the next sync reads every record in full, re-scrubs it under the new rules and remembers it afresh. What no table shows is a change to the code that applies the rules, to the decoder or to a mapper: that still needs `DecoderVersion` raised, as before. The signature is part of the digest, so a run for one account (`--account`) can neither refresh nor spoil another account's memory.
- **When a record is skipped.** A typed record is skipped when its digest matches and every row it produced still holds the remembered hash. A generic record is skipped when its live (not removed) row carries a matching digest. A skipped record is still seen (so removal marks are unchanged), its rows count as `seen` and `unchanged`, its account is refreshed and its people are merged in the same order, as a full read would have counted them. A record that is an omission (it did not decode, map or encode) is never remembered, so it is decoded again and counted again on every sync.
- **Two records, one row.** Generic records whose keys scrub to the same key share one row. Only the first record of a row in a read may be skipped; every later record that maps to the same row is read in full, in the original order, so the row and the counts come out as a full read leaves them on every sync. For typed records, a record that produced a row some other record of the source also produced is remembered as contended and is never skipped, so the records that share a row are read in full together, as a full read reads them. The first sync that meets such a pair finds out by a guard: if a record read in full rewrites a row that a skipped record of the same run vouched for, the source is rolled back and read again in full from the same snapshot (one extra read, once); from the next sync on the pair is read in full from the start and the source is read once.
- **Forcing a full read.** `sync --full-read` or `M365CRAWL_FULL_READ=1` reads every record of every source in full and still remembers, even a source whose fingerprint has not changed since the last sync (it does not stop at the fingerprint shortcut), so it checks the skipping exactly when the cache is stable. The archive is the same either way; use it to check. Under `watch`, the variable makes every sync that `watch` runs a full read.
- **Cost and bound.** About 16 bytes of digest per generic record plus a few bytes of redaction count, and per typed record its key, a 16-byte digest and 17 bytes per produced row plus the people it named: on a real cache of about 62,000 messages, 5,000 conversations, 1,000 activity items and 34,000 generic records, about 11 MiB (20,700 typed records, 10 MiB, most of it the people they named; 34,000 digests, under 1 MiB), 2.5% of a 765 MiB archive. The memory is bounded by the cache, not by the archive's age. A sync deletes the `typed_memo` rows of records that are no longer in the cache (in the same transaction; the archive rows they produced, and every `removed_at`, stay as they were, and a removed row never gets its mark cleared by this), and clears the digest of a generic row when it is marked removed (a record that returns is read in full). A read for one account (`--account`) forgets only within the databases it read. While a sync reads it holds the memory of one typed database at a time, the content hashes of the archive rows that memory names (looked up by rowid, never a whole table), and the digests of the live rows of one generic database: sized by the largest database in the cache, not by the archive. It avoids decoding the skipped records, so peak memory is lower, not higher.

**Consistency.** Teams keeps writing while m365crawl copies. The copy order, the retry and the validation above give a self-consistent copy or a `snapshot_inconsistent` error. A truncated tail in the active log file (Teams was mid-write) is tolerated and counted as the omission `truncated_log_tail`. Because each source is one transaction, a reader never sees half a source. A source that fails leaves the archive as it was for that source, and the next sync retries it.

**Omissions.** A record m365crawl cannot decode or map is skipped, counted by reason in `omissions`, and never guessed. A sync with at least one omission other than `denied_database` and `denied_store` (including `database_unreadable`) has status `ok_with_omissions` and still exits 0. The two denial codes count the credential denylist at work, not lost data, so they appear in `omissions` but never change the status.

| Reason code | Meaning |
| --- | --- |
| `empty_value` | The record has no value (Teams leaves some records empty). |
| `unknown_envelope` | The record's Blink envelope is not recognized. The detail ends with the first 16 bytes in hex. |
| `snappy_too_large` | A snappy envelope declares a decoded length above 32 times its compressed length (the densest valid Snappy is about 21:1), so the header is forged or damaged. It is refused before anything is allocated. The detail ends with the first 16 bytes in hex. |
| `blob_missing` | The record's value is stored in an external blob file and the blob entry or file is absent. |
| `bad_key` | The record's IndexedDB key could not be decoded. |
| `v8_version` | The V8 serialization wire version is not supported (13 to 16 are). |
| `v8_malformed` | The V8 payload is damaged or fails any other decoding rule. |
| `v8_unknown_tag` | The V8 payload uses a tag m365crawl does not know. |
| `v8_host_object` | The V8 payload holds a host object, which structured clone does not produce for Teams data. |
| `v8_shared` | The V8 payload holds a SharedArrayBuffer or shared object. |
| `truncated_log_tail` | The active LevelDB log ended mid-record (Teams was writing during the copy). |
| `unmapped_record` | The record decoded, but lacks its identity (for example no message id or conversation id) or is not an object. |
| `denied_database` | A database whose name matches the denylist (section 2) was skipped without being opened for values. Only the count is reported. |
| `denied_store` | An object store whose name matches the denylist was skipped inside an allowed database. |
| `database_unreadable` | A generic database (or the whole batch holding it) failed to read with a fatal error and was left incomplete; the other databases and the typed data still synced. It is data loss, so it makes the sync `ok_with_omissions`. Rows already archived for that database are kept and not marked removed. |
| `unencodable_value` | A generic record's value decoded but cannot be written as canonical JSON. Its key is still archived, with a NULL value. |

A new omission code may be added in a minor release. The `sources[].omissions` map in a report breaks the totals down by source.

**Report statuses.**

| Status | Meaning | Exit |
| --- | --- | --- |
| `ok` | Every source synced and nothing was omitted. | 0 |
| `ok_with_omissions` | Every source synced; at least one record was omitted. | 0 |
| `unchanged` | No source's cache changed since its last successful sync. | 0 |
| `partial` | At least one source committed and at least one failed (or the run was interrupted after one committed). The report is printed on stdout and a `partial_sync` error on stderr. | 1 |
| `failed` | No source committed. No report is printed, only the coded error of the first failure; the attempt is recorded in `sync_runs` as `failed`. | the error's |

Each entry of `sources` (in every report, not only a partial one) has a `status` (`ok`, `ok_with_omissions`, `unchanged`, `failed` or, for an Outlook source, `skipped_interval` or, when Outlook is on by default and could not be read, `unavailable`, which carries the `error` and changes neither the run's status nor its exit code). A source that was decoded and committed also lists its `accounts` (`<tenantId>/<userId>`) and `counts` (`conversations`, `messages`, `people`, `activity`, `records`, each with `seen`, `inserted`, `updated`, `unchanged`); an `unchanged` source has neither; a failed or unavailable source has `error: {code, message}`. The top-level counts add up the committed sources only.

The report also carries `failed_source_health`, an array of the current run's failed source/account entries in the shape and mapping of section 6.4. It is `[]` when no participating source/account maps to an entry; another account's retained failure remains available to later unfiltered reads. It does not change existing status values or exits. Schema 20 retains missing source refusal codes in the existing `sync_runs` outcome history, including discovery failures before an account is known; it adds no independent health tracker. A failure to persist or derive health returns `db_error`, preserving any original source or cancellation error, and records no fresh run success. An uncomputed health array is not reported as checked-empty.

### 4.2 The Outlook source (on by default)

The sync reads the new Outlook for Mac store as a second source, after every Teams source has finished. It is on by default: when the default Outlook profiles directory exists and holds a profile, no flag is needed. `--outlook-root DIR` (`M365CRAWL_OUTLOOK_ROOT`) reads DIR instead, and `--outlook-root none` (or `M365CRAWL_OUTLOOK_ROOT=none`) turns Outlook off. `M365CRAWL_OUTLOOK=1`, which used to turn Outlook on, is still accepted and has no effect. The hermetic rule stays: an explicit `--teams-root` without an explicit Outlook root keeps Outlook off, so a run pointed at a fixture never reads a real profile. Each profile directory holding an `HxStore.hxd` is one source, `outlook|<profile>`, with calendar account `outlook/<profile>`. It is never part of a `--account` run, which names a Teams account. With Teams not installed (`teams_not_installed` or `no_teams_origin`), Outlook runs alone when it has a profile to read; when Teams discovery fails for any other reason the run fails before Outlook is tried. **On by default means best effort.** A default Outlook never fails or holds up a Teams sync, and it changes neither the run's status nor its exit code. A machine with no new Outlook (no profiles directory, no profile, or an operating system that has none) says nothing. A profile that cannot be read (`no_full_disk_access`, `outlook_profile_unreadable`, a store version or layout this build does not read, a failed copy) is a source with status `unavailable` and its `error` `{code, message, fix}` in the report; the same failure is remembered per profile and shown by `calendar sources` and `doctor` as for any Outlook failure, and the next sync tries again after the minimum read interval. When Outlook is named (`--outlook-root DIR`) it is asked for, so having nothing to read is a failure as before: no profile under the root is the failed source `outlook` with code `no_outlook_profiles` (its fix names `<root>/<profile>/HxStore.hxd`, and says so when `HxStore.hxd` sits directly in the root), and a profile that cannot be examined is its own failed source (`no_full_disk_access` or `outlook_profile_unreadable`). Profiles of the old Outlook are listed in `outlook_classic_only`, a note and not a loss. A named root that does not exist, cannot be read or is not a directory, is the coded error `outlook_root_missing` (exit 3, with a `fix`), given the same way, before anything is read, by `sync` and by every read command (the implicit sync included, even when the archive is fresh enough to skip it). A named root that exists but holds no profile keeps `no_outlook_profiles`. `doctor` reports the root itself and is not stopped by it. `whoami`, `status` and `version` are never stopped by it either (a stale setting must not break the commands that look at the setup): their exit code is unchanged, and `status` carries the same `code`, `message` and `fix` as an `outlook` object. The calendar and every other read command keep the error.

- **Read-only copy.** The store file is copied once into a private temporary directory (never the lock or side files) and read from the copy, which is removed on every exit. At most one copy is made per `OutlookMinReadInterval` (5 minutes, assumed), measured from the last attempted copy and kept in `meta`, so a failing store is not retried in a loop. A skipped read is the source status `skipped_interval` with `next_read_after`, and carries the omissions of the last read (a skip never hides a loss). A skip writes no `sync_runs` row. If the read before the skip failed, the skip is that failure again (the same status `failed` and code, a `failed` row in `sync_runs`, and the run is `partial` or `failed`) until a read succeeds. A last attempt later than the run's start (the clock moved back) does not hold the source off.
- **Fingerprint.** The file's size and modification time plus the store version byte, the reader version, the Outlook mapper version and the scrub rules version. An unchanged store reads nothing and reports the losses of its last read. A change to the mapper version reads an unchanged store again.
- **Mail.** Mail follows the Outlook source: the same profile, the same private copy (one copy serves the calendar and the mail), and a source row of its own, `outlook|<profile>|mail`, with `counts.mail` (`added`, `updated`, `replaced`, `gone`, `evicted`, `withheld`). The calendar is committed and its memory released before the mail bodies are read. A refusal or failure in one never stops the other (the run is `partial` when one failed and one committed). The mail mapper version is part of the fingerprint, and an unchanged store skips the mail read only when the archive holds the account's read marker (`meta` key `outlook_mail_read:<account>`, removed by a failed mail read), so an archive written before mail reads it on the next sync. On Windows mail is not read: the row is `unavailable` with code `mail_unsupported_platform` and the sync does not fail. A mail folder's kind is `inbox`, `archive`, `drafts`, `sent` or `deleted` from the store's well-known folder type; the generic type 0x7a, which user-created folders, To Me, Junk Email and other system folders share, is `other`, except that a 0x7a folder holding a copy of a message that also has a copy in an inbox folder is `to_me`. Junk Email is not detected and no folder is ever `junk`.
- **Guard.** `outlook_store_unrecognized`, `outlook_store_version` and `outlook_layout_unsupported` fail the Outlook source (a coded source failure; the run is `partial` when Teams committed) and apply nothing. A damaged-block share over 2% is the loss `outlook_blocks_damaged`; an event that does not map is `calendar_unmapped`; one the core refuses is `calendar_refused`. An all-day flag whose times fit no whole-day shape is stored with the flag unknown and counted as `calendar_all_day_unaligned` (not a loss).
- **Outlook strings and all-day events.** An Outlook event with no location or no body preview has an empty `location` or `body_preview`: the store marks an absent string with a zero length word, and the mapper reads a string only when it is present (`outlookcal.MapperVersion` 5; before, an absent string read as the subject). An all-day HxStore Outlook event has `all_day` true, `start` and `end` at midnight UTC and `time_zone` `UTC` (the store's own label, not the owner's zone); read its day from `start_date` and `end_date` (the end is exclusive), which the agenda uses to place it, and not from the instants.
- **Apply.** One transaction per profile: the events go through the calendar core under the calendar savepoint (a failure rolls the profile back and fails that source alone), covered days are the days on which the store holds at least one event that is not a series master (cumulative, in the machine's zone; a zone change takes the days of archived events again), and an event Outlook stops holding is marked gone only when two consecutive reads that lost nothing (no `outlook_blocks_damaged` and no `calendar_unmapped` loss), taken from different copies of the store (a newer modification time), both miss it, so one torn copy that hides a live event for a single read changes nothing (the first miss is kept in `meta.outlook_absent:<account>`, a read that lost something or an event seen again forgets it, and a changed stamp keeps it); the event must also not be a series master and starts no earlier than 60 days before the read (`store.OutlookGoneHorizon`; Outlook keeps a rolling window that reaches about 99 days behind now and drops older events without a deletion, so an earlier one is taken as evicted and stays live). Outlook writes no deletion marker: a deleted event's objects stay readable and unchanged until Outlook compacts the store, minutes later, and then vanish, so absence is the only signal (docs/outlook-store.md, "Deleted events"). A read that would remember more than 20 events and more than 10 percent of the live events it judges marks none (the store looks reset). A marked event keeps all its data and is live again when a later read holds it. A deleted event can therefore stay listed until Outlook compacts and two syncs, at least the read interval apart, have read the store afterwards. `meta.outlook_read:<account>` keeps the census of the last good read (unknown layouts, blocks found and damaged, unmapped values; numbers only) for `calendar sources`, `meta.outlook_skipped:<profile>` says the last sync skipped the read because of the interval (the next sync that looks at the store forgets it), `meta.outlook_checked:<profile>` is when a sync last looked at the store, and `meta.outlook_derivation:<account>` stamps the mapper version, zone and scrub rules the profile was derived under; when it differs, each event of the batch is blanked before it is applied, so a stored value an older mapper wrote (an all-day flag stored as false) can become unknown instead of being kept over the unknown flag.

- **Merged lists are unions.** A linked twin's attendee list and structured location (room) list are the union of the two copies' lists, not the list of the copy with the newer clock: in 67 of 67 real twins that carry both lists the Teams list is the longer, and the Outlook copy is the newer in 146 of 148, so choosing by clock hid attendees. Attendees match by lower-case address, or by lower-case display name when an entry has no address; rooms match by lower-case name, or by address when a room has no name. For an entry both copies hold, the response, type and role come from the copy whose list clock (the `attendees` or `location_list` field clock, else `detail_as_of`, else `last_modified`) is newer; an entry only one copy holds is kept. A list the union enlarged beyond the one the detail rule chose is named in `filled_fields` (`attendees`, `rooms`), and `attendee_count` is the merged length. Every other field keeps its clock rule. An event only one source holds, or whose other copy has no list, keeps its list verbatim.
- **Teams owns the Teams meeting.** In a linked twin, the meeting-link unit (join URL, short join URL, dial-in conference id and toll number, and the meeting chat id) comes from the Teams copy when it states it, whichever copy is newer; the Outlook copy fills the unit only when the Teams copy lacks it. Recordings and recaps attach by the meeting chat id and the event's key, so they stay with the twin. An event a Teams copy says is an online meeting stays `is_online_meeting: true` while its join link is kept; the history rule (an organizer's later "not online" that removes the links) is unchanged. `rooms` is the union of the structured list and every place either copy's location text names, while `location` stays the schedule base's text.
- **Overridden fields.** `overridden_fields` (`[{"field", "from", "as_of"}]`) on an agenda item or event lists each field both copies of a linked twin stated with different values, and the source whose value the merged event holds (`union` for a merged list). It sits beside `filled_fields`, which lists fields only one copy stated.
- **Link.** An Outlook profile is its own principal until it is linked, by the operator or by proven identity (below). `--outlook-account <tenantId>/<userId>` (`M365CRAWL_OUTLOOK_ACCOUNT`) links the profile to that Teams account with the method `config`; `none` ends the link and keeps it ended (it records an ended `config` row even for a profile that had no link, so an automatic link never makes it again). With more than one profile under the root, `--outlook-profile NAME` (`M365CRAWL_OUTLOOK_PROFILE`) says which; `none` without a profile ends every link. The link is applied at the end of a sync, after the Teams sources, so the very first sync can name the account it creates, and it is kept in `calendar_account_links` (nothing is deleted: an unlink sets `unlinked_at`), so the flag is needed only to change it. Repeating a link that is in place, or ending one that is not, changes nothing. `none` also ends a link whose profile directory is gone: its profile names come from the archive's active links as well as from disk, and `--outlook-profile` may name one only the archive knows. The flags are read by the commands that sync or read the calendar and by no other (`whoami`, `status` and `version` ignore them); a value that came from `M365CRAWL_OUTLOOK_ACCOUNT` alone while the Outlook source is off is a warning, and the same value as a flag is a `usage` error. With `--max-age 0` the implicit sync is off, so a link still waiting to be applied is a `usage` error whose fix is the `m365crawl sync ...` command to run. A read command given the flag syncs first when the archive does not show the link as asked for. Nothing links by overlap, because two people invited to one meeting hold the same events; a link is either the operator's say or an identity match. A Teams account the archive has not seen, a malformed account, the flag without the Outlook source on, a profile name that is missing, unknown or needed, a Teams `--account` filter on a `sync` that links, and a second profile for an account that already has one are `usage` errors (exit 2) with a fix; the sources of that run are already committed, and `sync` still prints its report. Both sources key an event by its iCalUID, which Teams writes in lower-case hex and Outlook's store holds in upper case, so the Outlook mapper lower-cases it (and the series id it derives): that is what lets the twins meet. Linked, the Outlook rows are grouped under the Teams account: events both hold merge into one item with `sources: ["teams","outlook"]` and `filled_fields`, scalar fields by the clock rules and the attendee and room lists by union (below), an Outlook-only event gains the account's `tenant_id` and `user_id` and a new `event_id` (the id it had unlinked still resolves, and so does the linked id after an unlink, from the link history; an id some event has today wins over such an old one), a day either source covers is covered, and a meeting Teams marked gone stays hidden unless the Outlook copy was edited after the removal (section 3.2). Unlinked, `calendar --account <tenantId>/<userId>` omits the profile's events, an all-accounts agenda shows each twin once per principal, and the envelope names the profile in `unlinked_accounts` with the command that links it in `unlinked_fix`.
- **Automatic link by address.** After the sources have run, each profile is linked to a Teams account when, and only when, an address of an account signed in to the profile equals that Teams account's own address, compared without regard to case. That is an identity match, not an overlap guess, and the method is `address` (`calendar sources` shows it as `link`). The profile's addresses are read by the Outlook read from its account objects (class 0x49, tag 0x19d0, one record per signed-in account, rewritten as the store changes): the string at +5532 (an offset word relative to the string area, which starts at the tag plus the word at +104, and a length word after it that must equal the text's byte length with its terminator, so a record of that class with no address, whose string word and length word are 0, is refused), which must be written again alike at +5556 with its own words. Such an object is taken even when the walk reached it after unknown bytes (the account objects of a real store all are). A read keeps the distinct addresses, lower case, in the archive's `meta` table (`outlook_identity:<account>`, one per line); they are never printed, and a read that finds none keeps the empty string. A Teams account's own addresses are the `userPrincipalName`, `mail` and `email` of the record the account keeps of itself: store `profiles` of its own database, the key `"8:orgid:<userId>"`. A match needs exactly one Teams account that has one of the profile's addresses, ignoring an address that another profile also holds, and no other profile matching that Teams account; two Teams accounts with one address, two accounts in a profile that name two Teams accounts, two profiles with one address, no match or no address all leave the profile unlinked and the `unlinked_accounts` notice in place. A profile with a second account (a personal address, say) still links by the one that matches, and then belongs to that Teams account whole, as it does under an explicit link. A row the operator wrote is never changed: an explicit link, an explicit `none` and an explicit link that names the same account as an automatic one (which makes it the operator's) all stay. An automatic link whose evidence goes away (the addresses changed, or they no longer match exactly one account) is ended by the next sync, and made again when they match. The step never fails a sync. An archive written before the addresses were read has no `outlook_identity` row, so its first sync reads an unchanged store again to get it.

| `metadata` | Prints the crawlkit app manifest (a `control.Manifest`: `schema_version`, `id` `m365crawl`, `display_name`, `description`, `binary`, `paths` with the default database `~/.m365crawl/m365crawl.db` and `M365CRAWL_DB`, the `status`, `sync` (`mutates`), `doctor`, `search`, `calendar`, `transcripts` and `transcripts show` commands (and the overview and mail commands) as `m365crawl --json <command>`, `capabilities` (with `transcripts`), and `privacy` with `contains_private_messages: true`, `exports_secrets: false`, `local_only_scopes: ["teams_cache", "outlook_store"]` (`outlook_store` is the new Outlook for Mac store, read only when the Outlook source is on)) as one fixed-shape JSON document on stdout, indented in every output mode and regardless of `--format`, exit 0. Filter values: `--since` and `--until` accept RFC3339, `YYYY-MM-DD` (local midnight) or a relative duration such as `90m`, `24h`, `7d`, `2w`. `--from` takes a person id or a case-insensitive part of a name. `--team` takes a team's exact name (case-insensitive for ASCII letters only) or its id; an unknown or ambiguous name is a `usage` error that lists the matches.

Teams links: `--conversation` (on `messages`, `search` and `unread`), `thread` and `transcripts <meeting>` accept a link from `teams.microsoft.com`, `teams.cloud.microsoft`, `teams.live.com`, `gov.teams.microsoft.us` or `dod.teams.microsoft.us`, its ids percent-encoded or not; a link from any other host is a `usage` error. A pasted link is tidied first: surrounding spaces, the `<>`, quotes or backticks around it and trailing sentence punctuation (`.,;:!?)]}>'"`) are dropped, and the scheme matches in any case. A channel link (`/l/channel/<conversationId>/<name>`), a chat link (`/l/chat/<conversationId>/...`) a meeting link (`/l/meetup-join/<conversationId>/...`) and a team link (`/l/team/<conversationId>/conversations`, the team's General channel) name a conversation; a message link (`/l/message/<conversationId>/<messageId>`, with `parentMessageId` for a channel reply) names a conversation and a message. `--conversation` with a message link reads the link's conversation and its `note` says the link named one message and that `thread '<link>'` reads its thread. A chat link that names people instead of a chat (`/l/chat/0/0?users=...`) has no conversation id: it is a `usage` error whose `fix` says to find the chat with `m365crawl conversations --query <name>`. When the archive holds no conversation the link names, the empty result's `note` says so ("for this account" with `--account`) and that the Teams desktop app may not have cached it, and to open it once in Teams and then run `m365crawl sync`.

### 6.2 Streams and documents

- Results go to stdout. Progress, warnings, hints and the implicit-sync notice (section 6.4) go to stderr. Sync progress lines print only when stderr is a terminal.
- In JSON mode (including every non-TTY run) a command prints exactly one JSON document on stdout, compact on a pipe and indented on a terminal. Two exceptions: `watch` prints JSON Lines (section 7), and `skill` prints raw Markdown in every mode, as `--help` prints help text. `metadata` always prints one fixed-shape JSON document, indented in every mode, whatever `--format` says.
- Keys are snake_case and stable within 1.x. Additive fields are compatible when existing meaning, types and null/omission semantics are preserved; incompatible changes require a new major release, not just a changelog entry (section 10). Optional fields are omitted when empty, except the always-present and explicitly nullable fields documented for each command/source. Times are RFC3339 UTC unless a native shape explicitly preserves its source offset or literal. Links keep a literal `&`.
- `source_health: []` is an explicit exception to omission when empty: it means the participating sources were checked and have no reportable failure. When `needs_sync` is true, omit it unless a recorded failure produces an entry. `failed_source_health` is an array on sync reports, including `[]`.

### 6.3 List results

Every list command returns:

```json
{"items": [], "count": 0, "truncated": false, "archive_age_seconds": 0}
```

- `items` is always an array. `count` is its length. `--limit` (default 50, at least 1) caps it.
- `truncated` is true when more matches exist than were returned.
- `total` is the exact number of matches ignoring `--limit`. It is present only when `truncated` is true; otherwise `count` is the total. `sql` results never carry `total`.
- `channels_excluded: true` appears on `unread` and `messages --unread` when channels were left out; it is omitted when they are included.
- `note` is one plain sentence on an empty list (Teams, calendar and mail lists alike) saying why it is empty: no archive yet, no data of that source yet, a time range outside what the archive holds (naming the window), filters that matched nothing, a source this operating system does not read, or an `--account` the archive does not hold. It is additive and omitted on a list that has items, except where a command documents its own use (`mail unread`, `mail thread`).
- `archive_age_seconds` (below) and the optional `sync_error`, `needs_sync` and `hint` fields close the document.

### 6.4 Freshness and degraded answers

An Outlook discovery barrier before any profile names are known uses `account_id: null`; a named unreadable profile keeps `outlook/<profile>`. Shared directory/capture refusals produce a mail outcome when no independent mail outcome exists. Calendar-only refusals never replace mail health.

`source_health` discloses source failures that can hide missing items even when the archive has a recent complete sync. Each entry has `source` (`teams`, `outlook_mail` or `outlook_calendar`), `account_id`, `doctor_check`, `state` (`failing` or `never_succeeded`), `last_error_code`, `last_ok_at` and `newest_item_at`. Both `source` and `state` are open vocabularies. Outlook accounts use `outlook/<profile>` even before the first successful read; Teams uses `<tenantId>/<userId>`, or null if discovery failed before an account was known. `doctor_check` is `mail_readable` for mail, `outlook_store` for the Outlook calendar, and null for Teams. `last_ok_at` is null when no successful read is recorded. `newest_item_at` is the account-wide newest archive write/modification time, independent of query filters and provenance, and null when nothing is archived; it is never an event's future start time or a mail received/sent time.

Health uses the latest persisted per-source attempt after any implicit refresh; `--max-age 0` reads the last recorded attempt without writing. `ok` and `ok_with_omissions` clear failure. `unchanged` clears it only when its fingerprint was qualified by a successful read. `skipped_interval` carries the previous entry. `failed` maps to `failing`, or `never_succeeded` before any success. Unavailable layout/version refusals, `no_full_disk_access` and `outlook_profile_unreadable` use the same mapping. Unavailable `mail_unsupported_platform`, `no_profile`, `no_outlook_profiles`, `teams_not_installed` and `no_teams_origin` have no entry. Any other unavailable code maps to `failing`, so unknown refusals are never silent. Disabled sources have no entry; a profile that disappeared clears at the next successful sync discovery. A source in another family cannot clear an entry.

Scope follows the command's source/account selection and existing calendar principal links, not the items returned. Calendar event's related-mail query reads every mail account, so its mail health covers every mail account while calendar health follows the event principal. A failed mail source therefore remains visible when shared search returns only chats or no hits. Mail show/thread use their ID's account, not every mail account. SQL covers all three families. Each entry adds a notice naming the source, account when known, last successful read when known, failure code, possible missing newer items and `m365crawl doctor`. Text renders it as a `notice:` line; no new stderr lines are added. Mail show's field is at the message's top level, outside projection. The existing mail-only warning remains compatible.

Mail modification clocks include body fills, attachment/recipient writes, metadata fills, folder changes, rekeys, replacements, disappearance/reappearance marks and derived-text writes. They do not change the published meaning of `state_seen_at` or advance for unchanged reads. Older read-only archives retain their recorded successful/failed outcomes without migration; missing error codes stay unknown unless a retained legacy refusal supplies one. Legacy mail clocks use the latest recorded first/state/mark time. Writable migration backfills only that evidence, not the migration time; historical body/child write times that were never recorded cannot be reconstructed. Resolving a source's account identity retains its qualified successful history without clearing another account's failure.

- `archive_age_seconds` is on every read result (the list commands, `sql`, `status`, `whoami`). The notes and documents commands, which read their own registered sources and not the Teams or Outlook sync, leave it `null`; the Loop commands fill it, because Loop is projected from records that sync archives. It is the number of seconds since the covered accounts were last fully synced, or `null` when no complete sync covers them. "Covered accounts" means the one in `--account`, or, for a read of every account, the stalest account. Only a run in which every source succeeded (`ok`, `ok_with_omissions`, `unchanged`) refreshes an account; a partial or failed run refreshes nobody, and `sync --account X` refreshes only X.
- `needs_sync: true` and `"hint": "run m365crawl sync"` appear together when there is no complete sync yet: the archive does not exist, has never synced, has only had partial or failed syncs, or was written by an older m365crawl whose next sync upgrades it. An empty result then reads as "no data yet", not "nothing matched". They are omitted otherwise. In text mode the same hint also prints on stderr as a `hint:` line; in JSON mode there is no stderr hint, because the result carries it.
- `notices` is a list of short sentences, present only when the result needs a caution an agent should read before trusting it. Two of them: when the range of a `calendar` agenda starts after an account's `teams_cache_fresh_at` (section 6, `calendar`), so the whole range is newer than the cache's last refresh, the notice gives that refresh time (with the account when the agenda covers several), and says that an event created or changed since then, such as a new invitation, is not listed until Teams refreshes it: open the Calendar in Teams, then run `m365crawl sync`. And when `calendar`, `calendar event` or `calendar actions` returns an event that Outlook holds (an item whose `sources` has `outlook`) and the Outlook source is off for this run (`--outlook-root none`, or `--teams-root` without `--outlook-root`), the notice says Outlook is not being read and that the Outlook data is archived and not refreshed, and gives the age of each Outlook account's last good read (`last read outlook/Work 3 days ago`; the ages are left out when no read time is kept). Text output prints each notice as one dim `notice:` line. A result with no Outlook event, or any result of a run with the Outlook source on, has no Outlook notice.
- If the implicit sync fails, the command still answers from the archive, prints the failure on stderr as `{"warning": {"code", "message", "fix"}}` (a `warning:` and a `fix:` line in text mode) and adds `"sync_error": {"code", "message"}` to the result. A partial implicit sync reports `partial_sync` the same way. Only cancellation by a signal turns it into an error.
- The implicit sync always covers every account, even with `--account`, so a filtered read never hides data from later reads. A held lock makes the implicit sync fail with `locked`, which becomes a `sync_error`.
- Reads work on an archive written by alpha.1 before its first upgrading sync; they treat it as having no complete sync yet.
- `--team` is validated before an implicit sync runs, so a mistyped team name fails fast. Its `usage` error names `m365crawl teams`.
- When a read runs the implicit sync, it prints one line on stderr first. In text mode it is plain: `m365crawl: syncing — archive is 2h14m old (max-age 15m)`, or `m365crawl: syncing — no complete sync yet (max-age 15m)` for an archive that has never synced. In `json` and `log` mode it is one JSON line, so every stderr line stays machine-readable: `{"notice":"syncing","reason":"stale","archive_age_seconds":N,"max_age_seconds":N}` (`reason` is `stale` or `never_synced`; `archive_age_seconds` is omitted when never synced). The result then carries `"synced": {"seconds": N, "status": "..."}` beside `archive_age_seconds` (`seconds` is how long the sync took, `status` the sync report's status: `ok`, `ok_with_omissions`, `unchanged`, `partial` or `failed`; for `whoami` also inside `archive`). Neither the line nor `synced` appears when the archive was fresh enough or `--max-age` is 0, and the line never goes to stdout. A failed or partial sync still adds `sync_error` and the warning.

### 6.5 Item shapes

Message items (`messages`, `search`, `unread`, `thread`; also `watch` message lines):

| Field | Rule |
| --- | --- |

| `mentions_me`, `pinned` | Always present, `false` included. |

| `edited_at`, `deleted_at`, `mentions`, `reactions`, `files`, `links`, `subject`, `html`, `text_truncated` | Omitted when empty or false. `html` appears only with `--html`. |

It prints the stored projection, not the raw message (`messages.raw_json`), as a JSON string to decode a second time, selected by the immutable row's `rowid`. These are the message's own claims, not a verified app identity. A list result that returns such messages carries `application_evidence_coverage` outside `--fields` shaping: `{"scope": "returned_teams_messages", "state": "observed"|"unknown", "mapper_version", "returned_messages", "states": {mapped, partial, absent, failed, not_derived}, "posted_by_app", "retained", "backfill_pending", "note"}`, where `posted_by_app` counts the returned messages whose served evidence names an app by a non-empty `app_id` or `app_name` (`mapped` only says the claims were read; it is a lower bound, and `note` says so, when a returned message is `not_derived` or `failed` with nothing served), computed after `--limit` (for `search`, after the merged limit, over chat hits only); `unknown` means no Teams message was returned.

`mentions` items are `{id, display_name}`; `reactions` items `{key, count, user_ids?}`; `files` items `{name, url?, type?}`.

Conversation items: `tenant_id`, `user_id`, `id`, `kind`, `display_name`, `member_count` and `favorite` are always present; `title`, `team_id`, `last_message_at` and `read_horizon_at` are omitted when empty.

Person items: `tenant_id`, `id`, `display_name`, and `last_seen_at` when known.

Team items (`teams`): `tenant_id`, `user_id`, `team_id`, `display_name`, `channel_count` and `unread_count` are always present; `last_activity_at` is omitted when no message time is known.

Store items (`stores`): `database`, `store`, `records` and `removed` are always present; `last_updated_at` is omitted when unknown.

Record items (`records`): `source`, `database`, `store`, `key_json`, `first_seen_at` and `updated_at` are always present; `tenant_id` and `user_id` are omitted when empty; `removed_at` is omitted for a live record; `value_json` is omitted when the value never decoded. `key_json` and `value_json` are the parsed JSON itself (a string key is a JSON string, an object value a JSON object), not strings holding JSON. Bytes appear as `{"$bytes": "<base64>"}`. With positive `--max-text N`, a `value_json` whose serialized JSON text exceeds N Unicode code points is replaced by a JSON string containing its first N−1 code points plus `…` (N=1: only `…`), and `text_truncated` is true. This decoded-JSON versus clipped-string union is intentional; the clipped string need not itself parse as JSON. Exact/short values retain their decoded JSON type; `0` is unbounded. When `--fields` includes `value_json`, `text_truncated` stays with it.

Activity items: `tenant_id`, `user_id`, `id`, `type`, `is_read`, `at`, `conversation_display_name`, `sender_name` and `text` are always present; `subtype`, `conversation_id`, `message_id`, `reply_chain_id`, `app_id`, `sender_id`, `message_sent_at`, `text_truncated`, `link`, `actor_id`, `actor_name` and `actor_inferred` are omitted when empty or false. `sender_*` is always the related message's author. `actor_id` and `actor_name` say who did the thing, by type: `reaction` and `reactionInChat` name the reactor on a best-effort basis: the user, other than the account (whose id is taken as `8:orgid:<user_id>`, the `self_id` of `whoami`), whose reaction with the item's subtype key is nearest in time to the item, read from the message's reactions. It can name the wrong person when several people used the same key at about the same time, or when a reaction was removed, so these items carry `actor_inferred: true`; `mention`, `mentionInChat`, `reply`, `replyToReply` and `follow` name the related message's sender; `msGraph`, `teamMembershipChange` and `threadActivity` have no actor in the data, so the fields are omitted, as they are whenever the related message is not archived. `actor_name` comes from the people table and is omitted when the name is not known. Activity types seen in real caches: `mention`, `mentionInChat`, `reply`, `replyToReply`, `follow`, `reaction`, `reactionInChat`, `msGraph`, `teamMembershipChange`, `threadActivity`. An unknown `--type` matches nothing and is not an error.

### 6.6 `--fields`, `--max-text` and `text_truncated`

- `--fields a,b,c` keeps only those top-level keys of each item, in the order given. An unknown key is a `usage` error that lists the valid keys for that command. Each list command's `--help` ends with a `--fields keys` section that lists the same keys, read from the same table the check uses, so help and check cannot disagree; `unread` lists its `--by-conversation` keys on their own line, and `calendar` also lists the keys only `calendar event` has. On `watch`, a key valid for either a message or an activity item is accepted. The list envelope keys (`count`, `truncated`, `total`, `archive_age_seconds`, ...) are never projected away.
- `--max-text N` bounds each supported displayed text/preview field independently to N Unicode code points (Go runes), including the trailing `…` when cut. It applies on supported list/search/detail/read commands, not to every field or one aggregate item/session budget. For a positive N, longer strings keep the first N−1 code points plus `…`; N=1 yields only `…`. Exact-N, shorter and empty strings are unchanged. Counting is on decoded string values, not UTF-8 bytes, JSON encoding, terminal columns or grapheme clusters; clipping can fall mid-word or split a combining/ZWJ sequence. Existing `text_truncated` and field-specific truncation flags report cuts. Native IDs/raw evidence, full SQL records and coverage summaries retain their existing contracts rather than inheriting this bound. `0` keeps all text. A negative value is a `usage` error: `--max-text=-1` prints `--max-text must be 0 or more`, and `--max-text -1` (separate argument) is rejected by the argument parser with `--max-text: expected int value but got "-1" ...`. Reapplying N to an already bounded value is unchanged with no new cut. When `--fields` includes `text`, `text_truncated` stays with it.
- Availability is command-specific, not list-only. Supported detail routes include `mail show`, `drafts show`, `content show`, `calendar event`, `calendar attendees show`, `people show`, `transcripts show`, `notes show`, `docs show` and `loop show`, alongside the applicable list/search routes, `watch` and the `content capture` receipt. `content show`, like ordinary supported routes, defaults to `0` (unbounded per-field text); its first-100-occurrence preview remains bounded separately. `drafts list` defaults to a 300-code-point text preview; explicit `--max-text 0` disables that clipping. `drafts show` defaults to full text/HTML and does not accept `--fields`; the other item-output commands advertise their own field keys in help. Accepting the flag does not mean every field is clipped.
- Raw cloud native-ID prefixes (at most 128 runes), terminal-width shaping, the `records` decoded-JSON/clipped-string union, and occurrence-preview limits are separate contracts. `--max-text 0` neither disables those independent limits nor turns a preview into a full SQL record.

## 7. `watch`

`watch [--every 60s] [--min-interval 60s] [--emit-initial]` keeps the archive current and tells the caller what changed. It is the one command that prints more than one JSON document: it prints **JSON Lines**, one compact object per line on stdout, flushed as each event happens. Every line has a `kind`.

How it runs:

1. It syncs once at start. By default that first sync is a silent baseline: its changes are not printed, so only later changes appear. `--emit-initial` prints them too.
2. It watches the Teams `.leveldb` and `.blob` directories with file-system events (kqueue on macOS). Events are debounced: a sync starts after the cache has been quiet for 2 seconds and at most 10 seconds after the first event of a burst, but never sooner than `--min-interval` (default 60 seconds, env `M365CRAWL_WATCH_MIN_INTERVAL`, `0` disables the pause) after the previous sync ended. Teams on a busy account writes its cache continuously, and a sync is a full read, so without the pause `watch` would sync back to back and keep a CPU core busy. Events that arrive during a sync or during the pause coalesce into one sync when the pause ends, and no sync runs if the cache did not change; the first sync at start is immediate, a stop signal during the pause exits at once, and a sync that fails because the archive is locked is retried after the short lock backoff, not after the pause. A negative `--min-interval` is a `usage` error. Consequently the archive can lag Teams by up to `--min-interval` plus the time a sync takes. A poll every `--every` (default 60 seconds) is the safety net when events are missed; it syncs only when the source fingerprint changed (a sync that runs with `M365CRAWL_FULL_READ=1` set is a full read of every record). If file events are unavailable, `watch` warns on stderr and polls.
3. It runs until SIGINT or SIGTERM, then exits 0. Shutdown joins its owned file-event pump and watcher-close call before returning.

Line kinds:

| `kind` | Shape | When |
| --- | --- | --- |
| `message` | `{"kind": "message", "change": "new" \| "edited" \| "deleted", "item": <message item>}` | A message was inserted, changed or newly tombstoned by a sync. |
| `activity` | `{"kind": "activity", "change": "new" \| "edited", "item": <activity item>}` | An activity item was inserted or changed. |
| `sync` | `{"kind": "sync", "report": <sync report>}` | After each sync that ran and emitted, one line, after that sync's change lines. |
| `migrated` | `{"kind": "migrated", "from": 1, "to": 2, "rows": N}` | The first sync upgraded an older archive. Printed before anything else, even for a silent baseline. It is not a change: no `edited` lines follow for those rows. |
| `error` | `{"kind": "error", "error": {"code", "message", "fix"}}` | A sync or check failed with a runtime error, including `partial_sync`. Watching continues, and an unchanged repeat of the same failure is reported once. |

`item` has the same shape as the matching `messages` or `activity` item and honors `--fields`, `--max-text` and `--account`. System pseudo-conversations are skipped. `change: "deleted"` means the message gained its `deleted_at`.

Partial syncs: when a sync commits some sources and fails others (`partial_sync`), `watch` first emits the changes of the committed sources and a `sync` line with `"status": "partial"`, then the `error` line. The fingerprints stay as they were, so the next pass retries only what failed and no change is lost. The first sync that commits anything is the baseline, exactly as for a normal first sync: its changes are printed only with `--emit-initial`. `--fields html` fills `html` as `messages --html` does.

Failures: a held lock prints a `locked` warning on stderr and retries after at most 5 seconds. Environment errors (`teams_not_installed`, `no_full_disk_access`, `no_teams_origin`, `archive_newer`) end the run with a plain error on stderr and exit 3. If the first sync fails and a later one succeeds, that later sync is taken as the baseline, its changes are not printed, and a `baseline_delayed` warning on stderr says so (its `fix` suggests reading the archive, or restarting with `--emit-initial`). In text mode (`--format text`) `watch` prints one human line per event instead of JSON.

Latency: a change reaches the output after Teams flushes it to its cache, plus the debounce (2 to 10 seconds) and one sync. Measured on a real cache, a message's sent time to its line took about 12 to 32 seconds (median about 17 seconds), most of it Teams' own flush delay.

## 8. Privacy and security

- **Read-only by construction.** There is no code path that writes to Teams' storage. The Teams cache is only ever opened for reading, and `sql` runs on a read-only database connection (writes, `ATTACH` and multi-statement queries are rejected before and by the connection).
- **No credentials, no standalone network client.** m365crawl never reads Teams tokens. Databases and object stores whose names match the denylist (section 2, which includes `Teams:auth:*`) are never opened for values or decoded, and values of other records are scrubbed of token-shaped material before they are archived: JWT-shaped substrings, the whole value (of any type) of any object key, or any V8 Map pair key, named `access_token`, `refresh_token`, `id_token`, `authorization`, `client_secret` or `password` (ignoring case), any string starting with `Bearer ` (ignoring case), and the value of a `sig=` query parameter in a URL (ignoring case), each replaced by `[redacted]`; record keys are scrubbed the same way, and two record keys that differ only in scrubbed material collapse into one row (over-redaction, never a leak). Credentials inside a string that holds JSON (up to four levels) and the `value` field of an object whose `type`, `name` or `key` field is one of those names are redacted too, and each sync clears (like the denylist purge) archived rows whose key changes when scrubbed. The sync report counts these in `redacted` (a count, not an omission). Message text in the typed tables is not scrubbed. m365crawl has no network client of its own: the only connection its code opens is to the loopback CDP port of a browser it explicitly started for `transcripts fetch`, `transcripts signin`, `content fetch page/stream` or `content signin URL` (section 1).
- **Network only inside a browser, only for explicit acquisition/sign-in.** `transcripts fetch`, `transcripts signin`, `content fetch page/stream` and `content signin URL` are the only network workflows, through Edge or Chrome with m365crawl's own profile (`browser` next to the archive, never the user's everyday profile) driven over the DevTools protocol on `127.0.0.1`; the Go code opens no other connection. Fetches run headless; only the explicit user-agreed sign-in commands show a window. Ordinary content reads are archive-only, never fetch or sign in, and never replay sharing tickets or temporary URLs. m365crawl never handles Microsoft tokens or passwords, registers an app or reads browser cookies/databases: scripts return bounded native metadata, supported page controls, selected transcript entries, states and counts; temporary download URLs never leave the page. Script arguments reach the page only as JSON. Browser output goes to the null device, and the debugging port is open on loopback for one run (pipe mode was rejected because Go cannot pass the extra pipes on Windows). Owned browser cleanup runs on success, error, timeout and signal, with forced-quit/orphan recovery; content publication follows successful terminal close. Native Windows content acquisition remains unqualified.
- **The archive holds message content verbatim.** That includes anything people pasted into a message: links with tokens or secrets, credentials, file names, customer data. `raw_json` keeps the full original record. Treat the archive like the chats it contains: do not commit it, sync it to shared storage or paste its contents into tools you would not show the original messages to.
- **File permissions.** On macOS the archive file and its `<db>.lock` file are mode 0600 and the default archive directory `~/.m365crawl` is mode 0700. On Windows the archive directory is the privacy boundary: the default `%LOCALAPPDATA%\m365crawl` directory (or `%USERPROFILE%\AppData\Local\m365crawl` when `LOCALAPPDATA` is unset) is secured before open. An existing custom `--db` parent must already grant only the current user and SYSTEM, with both effective access and object/container inheritance that propagates to children for each trustee. The macOS-style `~/.m365crawl` directory is a custom parent on Windows and is never silently secured. Before SQLite opens, any existing archive, WAL (`<db>-wal`), shared-memory (`<db>-shm`), and rollback-journal (`<db>-journal`) files must already be private; unsafe files fail with `db_error` without rewriting their ACLs. Missing companions inherit the private directory boundary when SQLite creates them.
- **Snapshots.** The temporary copy of the cache includes Teams' sign-in database. It lives in a private temp directory for the length of one source's sync (mode 0700 on macOS, current-user + SYSTEM ACL on Windows) and is removed on success, on failure, and on SIGINT or SIGTERM. At the start of a sync, a stale root is reclaimed only with positive, protected owner-death evidence as in section 4.1; age alone cannot remove another run's lazy-reader backing files. Unknown and legacy roots remain.
- **Full Disk Access** is required only on macOS (see [docs/full-disk-access.md](docs/full-disk-access.md)), for the Teams container and for the Outlook group container alike. On Windows the default Teams cache lives under LocalCache and is not TCC-protected. Without the grant a default Outlook is reported as unavailable and the Teams sync carries on.
- **The Outlook store is read-only too.** Outlook's `HxStore.hxd` is copied once into a private temporary directory and read from the copy (section 4.2); nothing is ever written to Outlook's storage. The one personal value read for matching, the addresses of the accounts signed in to the profile, is kept lower case in the archive's `meta` table and is never printed, logged or put in an error or a report.
- **The browser profile.** Explicit `transcripts fetch`, `transcripts signin`, `content fetch page/stream` and `content signin URL` use Edge (or Chrome) with m365crawl's own profile, the `browser` directory beside the archive (`~/.m365crawl/browser` on macOS, `%LOCALAPPDATA%\m365crawl\browser` on Windows). It is created readable by its owner only (mode 0700; on Windows it inherits the archive directory's private access list). It holds browser sign-in state, which m365crawl never reads: no cookie, profile database or credential store is opened, no Microsoft token is handled, and scripts return only bounded native content evidence, states and counts (temporary download URLs never leave the page). `doctor` checks directory permissions without opening anything in it. Disposable synthetic fixture mock-keychain opt-in is never an authenticated product-profile default.
- **The browser's lifetime.** m365crawl owns the browser it starts: it runs headless and invisible except for explicit `transcripts signin` and `content signin URL`, which require user agreement; it is closed with `Browser.close` and then its whole process group (Unix) or job object (Windows) is ended, then any other process started with its profile (`--user-data-dir`), on success, error, timeout, signal and force-quit; when the first process exits with status 0 before the debugging port appears, as Edge's launcher can on Windows, the launch keeps waiting for the port until its timeout (a non-zero status fails at once); a browser a killed run left behind is ended at the next launch.
- **Tests and docs use synthetic data only.** The committed fixture is written by a real browser from made-up records.
- **Release artifact signing.** Mandatory Darwin signing/notarization and intentionally unsigned, verified Windows artifacts follow section 9 and `docs/releasing.md`; missing signing configuration is not permission to publish unsigned Darwin assets.

## 9. Known limits

- m365crawl sees only what the desktop app has cached. History the user never scrolled to may be missing, and Teams evicts old messages from its cache, so the archive is complete only from the first sync that saw a message onward. Sync regularly (`--max-age` does it for you).
- macOS and Windows with the new Teams app are supported. Classic Teams and Linux are not. Contact stores, call history and pinned-message lists are mirrored only as raw `records` (canonical JSON of what the cache holds) until typed tables or mappers exist.
- The calendar holds only what Teams cached. Teams caches the days the user looked at, not a range, so coverage is a set of days (`calendar_covered_days`); a day it never showed is unknown, not empty. Attendees, body and rooms exist for the minority of events the user opened. Recaps expire in Teams (`expires_at`). A day on which every event was deleted vanishes from the cache and reads as eviction, so its deleted events stay live. `m365crawl calendar`, `m365crawl calendar event` and `m365crawl calendar actions` read it; `sql` on the `calendar_*` tables also works.
- A link of an Outlook profile, explicit or by address, says the whole profile belongs to that Teams account. The automatic link needs one of the addresses signed in to the profile to be an address of the Teams account's own profile record (`userPrincipalName`, `mail` or `email`); a profile signed in under another address, such as an alias or a personal one, stays unlinked and the notice says how to link it. If a profile also holds a shared or delegate calendar (not yet known), its events appear as the account's own after the link. Outlook writes no deletion marker; an event deleted in Outlook is marked gone once two consecutive reads find it missing from the store (section 4, Outlook apply), which happens only after Outlook compacts its store, so a deleted event can stay in Outlook-only agendas for a while. A linked twin is hidden by an Outlook removal as it is by a Teams removal (rule M0 of the merge: the removal wins unless a live twin was edited later), which is why one missed read never marks an event. A meeting Teams removed shows again when the Outlook copy was modified more than 5 seconds after the removal, so an edit made in Outlook, such as a response or a category change, can bring back a meeting Teams removed; the rule is kept on purpose, because an edit is evidence the meeting still exists. Outlook covers the days on which its store holds at least one event, so a day with no event reads as `coverage_gap` even where Outlook may be authoritative.
- Full Disk Access is required only for the app that runs m365crawl on macOS.
- OneDrive usage: only the usage file is read, not OneDrive's library or sync databases. A usage file with a write-ahead log or shared-memory file beside it is refused, never consolidated. There is no default discovery on Windows or Linux, only Business account folders are read by default, and no usage claim is linked to an archived person, chat or account.
- Read-only: no sending, reacting or marking read. Attachments and media are not downloaded.
- `search`, `calendar event` and `status` see only transcript text already fetched; a part whose notice cached only a sharing link (`share_only`) or a media-service id (`ams_only`) cannot be fetched by ids, so its text is never in the archive.
- `reply_count` and `last_reply_at` are counted from archived replies and can lag Teams.
- People display names follow the most recent sighting; after an archive upgrade a few can differ from what a fresh sync would give.
- Teams can change its storage layout at any time. m365crawl then fails with a named error or reports counted omissions; it never guesses. A new V8 wire version fails with the version.
- A multi-source sync is atomic per source, not per run: a `partial` sync leaves the committed sources in the archive (section 4).
- Some `msGraph` activity rows (Microsoft 365 notices) have an empty conversation, sender and text: the cache holds no message for them, so they have no `actor_*` either.
- `needs_sync` is advisory: a read of a never-synced archive with `--max-age 0` exits 0 with an empty result and `needs_sync: true`. Check for it before reading an empty result as "no match".
- Untitled group chats are named after a few members (`Ana, Ben, Chao +2`), so two chats with the same first members can share a name; select such a chat by `conversation_id`.
- `watch` latency is dominated by when Teams writes its cache, not by m365crawl.
- Darwin (macOS) release binaries MUST be Developer ID signed and notarized before publication. Missing Apple secrets or a failed signing/notarization gate block the release; signing is not conditional. Windows release binaries are intentionally unsigned and verified as downloaded artifacts (checksums, architecture and executable version) by the normal release pipeline. These artifact checks do not qualify additional native sources or platforms.

## 10. Versioning and compatibility

- Starting with 1.0, the supported public surface below is stable within 1.x. Incompatible public API changes require a new major release; a changelog entry alone is not permission to break 1.x. This does not retroactively make all 0.x releases mutually compatible. Compatible additions may include commands, additive fields and open-vocabulary error/omission/loss codes or activity types; consumers must tolerate unknown additions. Existing meaning, types, nullability, omission semantics and default acquisition behavior MUST NOT change incompatibly within 1.x.

| Public surface | Stable contract and explicit exceptions |
| --- | --- |
| Supported commands, flags and defaults | Documented command/argument/flag meanings and defaults, including explicit acquisition boundaries. `--max-age` defaults to `15m` for sync-backed reads; `0` disables implicit sync. Content, drafts and native-attendee reads are archive-only under their documented boundaries; the no-command overview never syncs. Registered-source reads (native people, notes, docs and Loop) may refresh already registered inputs under documented positive max-age, minimum-interval and qualification rules, including writable archive admission where implemented. Native people reads with `--max-age 0` perform no capture, discovery or archive repair; ordinary people reads never implicitly discover unregistered sources (section 3.0.1). Other registered-source families retain their own documented zero-age behavior. Unsupported source/cache layouts remain explicit limits, not success-shaped empty results. |
| Machine field names, types, null and omission semantics | The documented shape for each command/source, not a universal item shape. Native source shapes retain explicit null versus omission, literal offsets, unknown values and source qualification. Existing keys keep their meanings and types; consumers tolerate additive fields and open-vocabulary codes. |
| Formats and streams | Ordinary output defaults to text on a TTY, JSON otherwise. `log` uses a sanitized command-path label and the same compact JSON document. Results use stdout; progress, warnings and hints use stderr. `watch` uses JSON Lines with in-band runtime errors and continues as section 7 specifies (text mode is human event lines). `skill` is raw Markdown in every mode. Help is help text; `metadata` is fixed-shape JSON, indented regardless of format. Neither is an ordinary list envelope. |
| Errors and degraded answers | Ordinary errors use stderr and exits 1/2/3/4 by code; a second signal forces 130 with no error document. Successful results exit 0, including signal-stopped watch. Degraded archive answers retain warnings and conditional `sync_error`, not a silent claim of freshness; watch's in-band errors and terminal failures follow section 7. |
| Envelopes and freshness | Applicable lists retain `items` array, `count`, `truncated`; `total`, sync metadata (`synced`, `sync_error`, `needs_sync`, `hint`) and `notices` are conditional under section 6 and command-specific rules. SQL uses `columns`/`rows`, never `total`. `archive_age_seconds` is nullable: unknown coverage and independently registered-source reads are not measured zero. |
| Clipping and records | Per-field inclusive Unicode clipping follows section 6.6 and command-specific defaults. `records.value_json` intentionally has a decoded-JSON versus clipped-string union, with omission when never decoded. A clipping request does not normalize native shapes, IDs or all JSON to strings. |
| Published SQL columns | Only documented columns, keys, types, nullability and meanings are the SQL compatibility surface; internal bookkeeping columns remain internal even if queryable. Additions are compatible only when existing contracts remain intact. |
| Identity and revision scope | Stable IDs bind their declared source/account/native identity and algorithm, not a universal person or cross-app identity. Archive-scoped row IDs identify immutable observations only within the same archive, not portable native identifiers. Draft locators bind the documented source/account/native tuple; a draft body revision binds its retained wrapper and qualification frame, not the live editor, server-unsent state or whole draft lifecycle. |

Human prose, key order, whitespace and internal columns are not byte-stable machine contracts. Cache-layout universality, complete service history, all native platforms and universal identity resolution are not promised by 1.x; the source-specific support and refusal boundaries still apply.

- The archive has two distinct version numbers: the SQLite schema version (20) and the derivation version (2, section 3.2). Compatibility is directional: newer supported builds migrate older supported archives at the documented writable-open/explicit-sync boundary, not during archive-only reads. There is no downgrade promise: an older 1.0 binary is not promised to open every future 1.x archive. Higher schemas are refused on reads and writes with `archive_newer`; the separate derivation guard refuses before writes as section 3.2 specifies.
- Schema 20 adds retained source refusal codes/account scope to `sync_runs` and internal mail modification clocks; derivation version remains 2. `source_health` and `failed_source_health` are compatible additions. Consumers must tolerate new source/state values and preserve the documented distinction between omitted health, `[]`, and nullable identity/time fields.
- Migration history remains historical: schema 5 adds calendar tables, schema 6 mail tables, schema 7 transcript tables (filled from archived recording notices by sync), and schema 8 mail identity. Schema 12 adds `messages.raw_digest` and Teams message application evidence (filled offline by sync, section 3.0.3); schema 13 adds cached Loop tables (section 3.0.4); schema 14 adds Office registry variant columns and schema 15 OneDrive usage variant columns and relations (section 3.0.2). Schema 16 adds explicit cloud observations, schema 17 resident Office text, schema 18 Engage Home sessions, and schema 19 native calendar attendee evidence and link frontiers. None changes the derivation baseline of 2.
- The source fingerprint includes a decoder version; raising it makes the next sync re-read an unchanged cache, and the read memory signature includes it too, so that re-read decodes every record in full (section 4.1).
