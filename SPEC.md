# teamscrawl specification

Status: normative for v0.2.0.

This document defines what teamscrawl does and what its output promises. Where this document and the code disagree, that is a bug in one of them and is fixed in the same change that finds it. The words MUST, MUST NOT and SHOULD carry their usual meaning. Command-by-command flag tables live in [docs/commands.md](docs/commands.md); the reading path through the Teams cache lives in [docs/how-it-works.md](docs/how-it-works.md).

## 1. Purpose and scope

teamscrawl lets an agent on a supported desktop host read the operator's Microsoft Teams history quickly and offline. It mirrors the new Teams desktop app's local cache into a local SQLite archive with full-text search, then answers queries from that archive. Its primary users are agents, so it favors predictable commands, stable JSON, coded errors with a `fix`, and self-diagnosis over interactive features.

It never talks to the Teams service, never reads or uses Teams credentials, and never writes to Teams' storage. It has no network code.

In scope for v0.2.0:

- macOS and Windows with the new Teams app (`com.microsoft.teams2` / `MSTeams_8wekyb3d8bbwe`), every WebView2 profile, every Teams origin and every signed-in account found in them.
- Conversations (chats, channels, teams, meetings), messages (channel posts, replies, chat and meeting messages), the activity feed, read state, and people derived from message senders and conversation members.
- Every other Teams IndexedDB database that does not look like credential material (calendar, pinned messages, contacts, call history and the rest of what the app caches), mirrored generically into the `records` table until a typed mapper exists for it.
- Commands: `doctor`, `whoami`, `sync`, `status`, `search`, `messages`, `unread`, `activity`, `thread`, `conversations`, `teams`, `people`, `stores`, `records`, `sql`, `watch`, `skill`, `version`.

Out of scope: sending, reacting, marking read or any other write to Teams; using Teams tokens; classic Teams; Linux hosts (CI runs on Linux, but there is no Teams desktop cache to read there); downloading attachments or media (files and links are stored as metadata); a terminal UI.

## 2. Data sources and the credential denylist

New Teams runs an Edge WebView2 whose user data directory is `~/Library/Containers/com.microsoft.teams2/Data/Library/Application Support/Microsoft/MSTeams/EBWebView` on macOS and `%LOCALAPPDATA%\Packages\MSTeams_8wekyb3d8bbwe\LocalCache\Microsoft\MSTeams\EBWebView` on Windows (the default `--teams-root`). teamscrawl reads that directory as follows.

- **Profiles.** Every `WV2Profile_*` directory (any directory under the root that has an `IndexedDB` subdirectory).
- **Origins.** In each profile, every directory `IndexedDB/https_teams.microsoft.com_<n>.indexeddb.leveldb` or `https_teams.cloud.microsoft_<n>.indexeddb.leveldb` (with its sibling `.indexeddb.blob` directory). One profile and origin pair is one **source**, identified as `<profile>|<origin>`. Other IndexedDB origins are never read; `status`, `sync` and `doctor` list their names (`other_origins`) so drift is visible.
- **Databases.** Inside an origin, database names follow `Teams:<manager>:react-web-client:<tenantId>:<userId or 8:orgid:userId>:<locale>`. The tenant and user ids of an account come from that name.

teamscrawl reads every database in the origin except credential material. The rule is deny-only: a database or object store is read unless its name is denied, and the operator has ruled that agents get open access to all other Teams data.

**Typed databases.** These three have mappers and become the typed tables of section 3:

| Manager | Object store | Becomes |
| --- | --- | --- |
| `replychain-manager` | `replychains-2` | messages (each record is a reply chain holding a map of messages) and people |
| `conversation-manager` | `conversations` | conversations and people |
| `activity-manager` | `feed-items` | activity items |

A typed manager that is absent is skipped; one that is present without its object store fails the sync with `store_missing`.

**Generic databases.** Every object store that is not denied and not consumed by a typed mapper is read, record by record, into the `records` table (section 3.1) with the key and the value as canonical JSON. That is every store of every other database, plus the other stores of the three typed databases: only the exact `(manager, object store)` pairs in the table above are excluded, and a typed database whose only store is the typed one contributes nothing. This includes, on a real cache, pinned messages, contacts and call history until they get typed mappers. The read takes a census of the cache first (it knows each database's id, name and object store ids), groups databases in order into batches whose estimated memory is at most 64 MiB, and opens the cache once per batch with only that batch's kept object stores loaded: excluded and denied stores are never loaded into memory, and there is no second metadata pass. The census counts a whole database, so it can over-estimate a database with excluded stores; that only makes batches smaller. After each batch the heap is collected. A database larger than the budget is read alone. The peak is therefore about the larger of the budget and the largest single database's kept stores, plus the keys seen in the database being read: the set of keys seen is dropped as soon as that database has been compared with the archive (section 3.2), never accumulated over the whole read. A fatal error inside one database (not a cancellation) makes that database incomplete and counts one `database_unreadable` omission; the read continues with the next database, and a batch that cannot be opened does the same for every database in it. Sync and watch cost on a large real cache is not measured yet and is gated on a run on a work machine before release.

**The calendar is a projection of `records`.** Four of those object stores also feed the calendar tables (section 3.1): `calendar` and `calendar-internal-data` of `Teams:calendar:react-web-client:...`, `meetforwork-meeting-catch-up` of `Teams:meetforwork-manager:...` and `meeting-recap-catchup` of `Teams:meeting-recap-manager:...` (the list is `teamscal.ClaimedStores`; the `calendar-manager` / `events` store of the test fixture is not Teams' calendar and is not claimed). They stay in `records` and in `stores`: the calendar tables are derived from them (section 4, step 6), never a replacement. A recap record of `meeting-recap-catchup` is `{data, recapId, syncTimeUtc}` and its content (`callId`, summaries, `actionItems`, `atMentionEvents`, times) is under `data`; the mapper reads only that shape.

**Denylist.** A database name or an object store name is denied when, ignoring case, it starts with `Teams:auth` or contains one of `auth`, `token`, `credential`, `secret`, `cookie`, `msal`, `oneauth`, `key-store`, `keystore`, `keyval`, `session`, `key-value`, `keyring`, `crypto`, `encrypt`, `pkce`, `bearer`, `password`, `refresh` or `adal`, or has `aad`, `keys`, `jwt` or `e2ee` as a whole segment (delimited by the start or end of the name, one of `-`, `_`, `:`, `.` and `/`, or a camelCase boundary, so `userKeys` matches `keys` while `load` does not match `aad`). The list over-denies on purpose: a wrongly denied name costs one missing store, a decoded token costs a leaked credential. A denied database is never opened for values, walked, decoded, listed by name or logged; only its count appears, as the omission `denied_database` (and `denied_store` for a denied object store inside an allowed database). Adding a name to the denylist is a SPEC change; removing one needs the same review as adding a decoder. A name added to the denylist later is enforced on rows already archived: see "Credential purge" in section 3.2. Beyond names, values of allowed stores are scrubbed before they are archived (section 8).

## 3. The archive

The archive is one SQLite file (WAL mode) at `~/.teamscrawl/teamscrawl.db` on macOS and `%LOCALAPPDATA%\teamscrawl\teamscrawl.db` on Windows by default, overridable with `--db` or `TEAMSCRAWL_DB`. A relative `--db` path is resolved against the current directory. On Windows the default path is private by construction: teamscrawl creates the default directory boundary with a current-user + SYSTEM ACL before SQLite writes bytes. A custom `--db` path is allowed when its direct parent directory is already private enough or teamscrawl can create that parent itself as a new private directory; if the direct parent already exists and is not private, or the archive file already exists and is not private, open fails with `db_error` before SQLite opens the database. The archive's schema version is 5 (`schema_migrations`, shown as `schema_version` by `status` and `doctor`). Timestamps are stored as UTC text with millisecond precision and printed as RFC3339 UTC.

Rows are partitioned by account: `(tenant_id, user_id)`. Two accounts never mix. The user id is the bare GUID; the account's own sender id is `8:orgid:<user_id>`.

A message's `text` (`content_text`) is plain text derived from the HTML body: tags dropped, entities decoded, an @-mention shown as the person's name, whitespace collapsed. For bot cards (Adaptive, hero and connector cards), call and meeting events, thread events and call recording or transcript notices, `text` is a readable summary (`Call ended · 23m`, `Member added`), never raw JSON. The original record stays in `raw_json`.

### 3.2 Archive semantics

- **The archive outlives Teams' cache.** Teams evicts old messages from its own cache as it runs. teamscrawl MUST NOT delete a message, conversation, person or activity item because it disappeared from the cache. No code path issues a `DELETE` against these tables (it only replaces the full-text rows of a row it updates).
- **Deletions are tombstones.** When Teams marks a message deleted, the row gets `deleted_at`. The row, its text and its `raw_json` remain.
- **`deleted_at` is sticky.** Once set, it stays set when a later sync sees the same or an older version of the message without it. A strictly newer version without a deletion clears it.
- **`--include-deleted` is off by default.** `messages`, `search` and `thread` hide deleted messages unless the flag is given. Deleted messages are never counted as unread.
- **Idempotent upserts.** A message changes only when the incoming `version` is newer, or the version is equal and the content hash differs. An older version is ignored. A second sync with no new Teams activity changes no row.
- **Unread** means: the message is newer than its conversation's `read_horizon_at`, is not deleted and was not sent by the account's own user. The horizon comes from Teams' consumption horizon in the conversation properties.
- **`mentions_me`** is true when the message mentions the account's own user by id, or the account's activity feed holds a `mention` or `mentionInChat` item for it (which covers channel, team, tag and @everyone mentions). **`mention_kind`** says which, computed at query time: `person` when the mention is by id or the feed item's subtype is `person`; otherwise the feed item's subtype (`channel`, `team`, `tag`, `everyone`), or `other` for a subtype this version does not know. A message that does not mention the account has none. A direct mention is `mention_kind` `person`.
- **System pseudo-conversations** `48:notifications`, `48:calllogs` and `48:annotations` are hidden from every list command unless `--include-system` is given, because they duplicate real messages without sender or conversation names. `48:notes` (the user's own notes) is not hidden.
- **Derivation version.** Text, sender names and untitled-chat names are derived from `raw_json` by the mappers. The archive records the mapper generation in `meta.derivation_version`; this build writes 2. An archive with no such row was written by alpha.1 (version 1). The first `sync` on an older archive recomputes the derived fields of every stored row from its `raw_json` (rows Teams has since evicted included), rebuilds their text indexes, and records the new version, all in one transaction before the cache is read. The recomputation counts as no update and no edit. An archive with a higher derivation version than the build's is refused with `archive_newer` before any write.

- **`records` follow the same rules.** A record that leaves the cache gets `removed_at` (a sticky timestamp) and keeps its last value; it is never deleted (the credential purge below is the one exception). This holds for one record gone from a store that was read completely, and for a whole database that is no longer in the origin (a filtered `--account` sync only marks that account's databases). A database read incompletely (a bad key, a `database_unreadable` failure, or a failure that fails the source) marks nothing. A record seen again clears `removed_at`. A record whose value cannot be decoded is stored with a NULL `value_json` the first time, and never overwrites a value stored earlier. A row changes only when its value's content hash changes. `updated_at` moves only then, or when a removed row returns.
- **Credential purge: the one exception.** Each sync, rows of the source whose database or object store name now matches the denylist get `value_json` NULL, `content_hash` empty and (when not already set) `removed_at`. This is the single case where the archive clears content it holds: credential material is cleared, not kept. The key stays. Rows already cleared are left alone.
- **Schema version.** A version 2 archive gains the `records` table in place when it is opened for writing, and its other rows are untouched. A version 3 archive gains the read-memory columns of `records` and the `typed_memo` table the same way (migration 4); its rows carry no memory yet, so the first sync after the upgrade reads every record in full. An archive whose schema version is higher than this build's is refused with `archive_newer`, by read commands too (`doctor` reports it as a failing check); builds before this one report that as a generic `db_error` instead.

- **The calendar tables follow the same rules, and keep the richest copy.** No code path deletes a calendar row. An event the cache stops holding is not deleted: it gets `removed_at` only when the cache still holds the event's day (the event was deleted, cancelled or declined away); an event whose whole day left the cache was evicted, and stays live. Teams fetches an event's attendees, body and rooms only for events the user opened, so a later, thinner copy never erases them: each unit of an event is compared against its own clock, a newer copy replaces it, an older or empty one does not, and where two copies are equally old the larger list wins (so an attendee removed at the same modification time can linger; `detail_as_of` says how old the detail is). A recap field group that arrives empty never replaces a stored one, and a recap item that a newer copy no longer lists gets `superseded_at` (a sticky tombstone), not a delete. The calendar tables hold attendee addresses and recap text, which are in the archive because they were in the cache.
- **Backfill and re-derivation.** The calendar is derived from `records`, which the sync keeps complete, so an archive upgraded from schema 4 fills its calendar on its first sync from the rows it already holds, without the Teams cache. `meta.calendar_derivation` holds the stamp `mapper=<teamscal.MapperVersion>;zone=<January and July UTC offsets of the sync zone, in seconds>;rules=<teamsdesktop.RulesStamp>`. A different mapper version maps every record again and captures it over what is stored. A different zone (covered days are taken in `time.Local` and never shrink, so days taken in the old zone would mix with the new) forgets the covered days and takes them again, from removed records as well as live ones, so a day whose events were evicted stays covered. A current stamp over empty calendar tables while calendar records exist (the tables were lost, the stamp was not) derives again. Different scrub rules (the stamp covers every rule table, and `teamsdesktop.RulesVersion` covers the code that applies them) additionally blank the content of every derived row first and rebuild what the records still back, so a copy made under an older rule does not outlive it; recap items that were blanked are marked superseded. The rebuild runs inside one transaction before any source is read.

### 3.3 Full-text index

`message_fts(message_key unindexed, content)` and `conversation_fts(conversation_id unindexed, title)` are FTS5 tables whose rowid equals the rowid of the owning `messages` or `conversations` row. The store maintains them in the same transaction as the upsert. `messages` and `conversations` are therefore rowid tables with no explicit integer primary key, and their rowids are load-bearing: an operation that renumbers them, such as `VACUUM` (SQLite documents that VACUUM may change the rowids of such tables), would silently detach the indexes from their rows. Nothing in teamscrawl runs `VACUUM`, and nothing outside teamscrawl SHOULD run it on an archive. If an archive's indexes are damaged, move it aside and run `teamscrawl sync` to rebuild a fresh archive from the cache.

A `search` query is split on whitespace into terms that are ANDed. `"quoted phrases"` match as phrases and a trailing `*` on a bare term is a prefix. Every FTS5 operator in the input is quoted, so it is an ordinary word.

## 4. Sync

`sync` mirrors every source into the archive once. A run proceeds as follows.

1. **Lock.** The run takes an exclusive, non-blocking lock on `<db>.lock` (a mode-0600 file on macOS, a current-user + SYSTEM protected file on Windows). The implementation uses `flock` on Unix and `LockFileEx` on Windows. If another sync or watch sync holds it, the run fails at once with `locked` (exit 4); it never waits. Read commands do not take the lock and work beside a writer.
2. **Sweep.** Snapshot directories named `teamscrawl-snapshot-*` in the temp directory that are older than one hour (left by a killed process) are removed.
3. **Migrate.** An older archive is re-derived as described in section 3.2, and the calendar tables are filled or rebuilt from `records` when the archive has none yet or was derived by another mapper or under other scrub rules (section 3.2, "Backfill and re-derivation"; this needs nothing from the Teams cache). An archive that is newer than this build fails with `archive_newer`, and nothing is written, not even a failed-run record.
4. **Discover** the sources (section 2). Errors: `teams_not_installed`, `no_full_disk_access`, `no_teams_origin`.
5. **Per source:** fingerprint, skip or snapshot, decode, map, write.
   - The **fingerprint** is a SHA-256 over the decoder version and the sorted name, size and modification time of every file in the origin's `.leveldb` and `.blob` directories, excluding `LOCK` and `LOG*`. If it equals the fingerprint of the last successful run for that source, the source is `unchanged`, nothing is decoded and no row changes, unless the read is forced with `--full-read` (section 4.1), which does not stop at the fingerprint. A run with `--account` records no fingerprint and never skips, so a filtered run cannot hide another account's data from a later run.
   - The **snapshot** copies the two directories into a private temp directory (mode 0700, files 0600), regular files only. LevelDB data files are copied first, then the `MANIFEST`, then `CURRENT`; blobs last. The copy is retried, up to three attempts, when `CURRENT` changed during the copy, the copied manifest is not the size of the live one, or a file the manifest names is missing. After three attempts the run fails with `snapshot_inconsistent`. The snapshot is validated by reading every table and log. It contains Teams' sign-in database, so it is removed when the source is done, on failure, and on SIGINT or SIGTERM.
   - The **snapshot** copies the two directories into a private temp directory (mode 0700 with mode-0600 files on macOS, current-user + SYSTEM ACLs on Windows), regular files only. LevelDB data files are copied first, then the `MANIFEST`, then `CURRENT`; blobs last. The copy is retried, up to three attempts, when `CURRENT` changed during the copy, the copied manifest is not the size of the live one, or a file the manifest names is missing. After three attempts the run fails with `snapshot_inconsistent`. The snapshot is validated by reading every table and log. It contains Teams' sign-in database, so it is removed when the source is done, on failure, and on SIGINT or SIGTERM.
   - **Decode and map** read the typed stores of the snapshot, then every other database that is not denied (section 2). A record whose stored bytes have not changed since the last committed sync is skipped, not decoded (section 4.1).
6. **Write.** Each source is applied in **one write transaction**: accounts, conversations, messages, activity items, people, generic `records`, the calendar tables derived from them (below) and the source's `sync_runs` row commit together or not at all. Records are applied in batches of 2,000 (or about 4 MiB of values) so memory stays bounded. Right after each generic database is read, its rows that are no longer present get `removed_at` when it was read completely, and the keys seen are dropped; after the last one, rows of databases the origin no longer holds get `removed_at` too, and rows under a name the denylist now matches are cleared (section 3.2). People are merged across the whole source; the newest sighting names a person. Sources are independent: a source that fails (including from a panic, which becomes `internal`) rolls back completely, is recorded as `failed`, and does not stop the sources after it. Sources that committed stay committed.
   - **Derive the calendar** (the last write of the source's transaction, after its records are written and before it commits). `DeriveCalendar` maps only the calendar and recap rows this sync inserted or changed (`records.updated_at` at or after the sync's start); with skipping (section 4.1) an unchanged record is not rewritten, so it is not mapped again. The days the cache holds now are read from every live calendar record by SQL (the start time and event type only, in the machine's zone), upserted into `calendar_covered_days`, and the window is the span of every covered day ever seen, so neither shrinks. A removed calendar record whose day is held now marks its event gone (`removed_at`, all data kept) only when no source that holds the account has the event live (two Teams profiles can hold one account, and an event keyed by account and source id is one event); one whose day is not held is eviction. A record that reappears clears it. Only an account whose cache this sync read (it found one of that account's databases) gets a fresh window, `synced_at` and covered-day `last_verified_at`: a sync of one account, or of a source that no longer holds another account, leaves that account's freshness as it was; a rebuild from the records reads no cache, so it keeps `synced_at` and re-verifies no known day. A record that cannot be mapped is the omission `calendar_unmapped` (a loss: it makes the sync `ok_with_omissions`); an event the core refuses is `calendar_refused` (also a loss). Both are counted on every sync, not only on the one that rewrites the record: the derivation keeps what it could not use in `calendar_losses` (per record, with a reason that names a field or a shape and never content), replaces a record's entries whenever it maps the record again, ignores a removed record, and reports what still stands for the accounts it read. A sync that finds the cache unchanged reads nothing, and still reports the stored losses of its source, so it is `ok_with_omissions` and not `unchanged` while data is missing (so is the run that upgraded the calendar); an event in a time-zone name teamscrawl does not know is stored and shown, `time_zone_iana` empty, and counted as `calendar_unknown_time_zone`; an all-day event whose times fit no whole-day shape is stored as timed and counted as `calendar_all_day_unaligned`. The last two are not losses. Recaps without an `ical_uid` are then linked to the one event whose start and end are within `teamscal.RecapTimeTolerance` (link method `time`), and those still unlinked to the one live, timed, non-master event that is neither cancelled nor declined and starts within five minutes of the recap's meeting start (`calendar.RecapStartTolerance`, link method `start_time`), because a recap's end is when the call ended, not the scheduled end. A start link is recomputed on every derivation: all `start_time` links of the account are cleared first and made again from the events as they are, so the result does not depend on the order rows arrived in, and a link that is no longer unique or whose event went is dropped. A link by id (`ical_uid`) or by both times is never touched, and an id that arrives later replaces a start link. Zero candidates or several leave the recap unlinked, never guessed. A link by id is placed at read time: when several live occurrences share the recap's `ical_uid` (a series id), the recap belongs to the one whose start is nearest its `meeting_start` within `calendar.RecapStartTolerance`, and a recap no occurrence matches stays on all of them as a series-level link (section 6). `linked_by_start`, `unlinked_no_event` and `unlinked_ambiguous` are a census of the account's recaps after the derivation (those with a meeting start and no id), not what the run changed. The derivation runs in a savepoint: a failure of a calendar write rolls back only the calendar, is counted as the omission `calendar_derivation_failed` (a loss), and does not fail the source, whose messages and records commit; the stamp `meta.calendar_derivation` is then dropped so the next run derives the whole calendar again from `records`.
7. **Record and report.** The run writes its run-level `sync_runs` row (section 3.1) and prints its report (section 5, `sync`). Only a run in which every source succeeded counts as a fresh sync, for every account (or for the one account of `sync --account`). A partial or failed run refreshes no account.

### 4.1 Skipping unchanged records

A sync of a changed cache does work in proportion to what changed, plus one cheap pass over the raw cache. The result is always exactly what reading every record in full gives: the same rows, the same `seen`/`inserted`/`updated`/`unchanged` counts, omissions and `redacted` count, the same changes for `watch`, the same `removed_at` marks and the same people.

- **What is remembered.** For each record a sync read in full and mapped cleanly, the archive keeps a 16-byte digest of the record's payload (the V8 bytes after the Blink envelope, snappy and any blob file are unwrapped, so a blob-backed value is covered by what the blob holds) taken under a signature, and what the record did. A generic record keeps its digest and its redaction count on its own `records` row (`raw_digest`, `value_redacted`). A typed record (reply chain, conversation, activity item) keeps its digest and its effects in `typed_memo`: the rows it produced, each with the content hash the row held afterwards, and the people it named with their sighting times. It is written in the same transaction as the rows, so a rollback or a crash forgets it with them.
- **The signature** covers `DecoderVersion`, the derivation version and every rule table of the scrub and the denylist: the secret key names, the regular expressions, the depth limit, the sibling-field names, the replacement text, and the deny prefixes, terms and tokens. They all live in one registry (`ruleSet` in `internal/teamsdesktop/rules.go`) that `Scrub` and `Denied` read and that the signature hashes field by field, so adding a key name, a pattern or a term changes every digest without anyone having to remember to say so, and a test fails if a rule table is declared outside the registry. Anything that changes how bytes become rows therefore changes every digest, and the next sync reads every record in full, re-scrubs it under the new rules and remembers it afresh. What no table shows is a change to the code that applies the rules, to the decoder or to a mapper: that still needs `DecoderVersion` raised, as before. The signature is part of the digest, so a run for one account (`--account`) can neither refresh nor spoil another account's memory.
- **When a record is skipped.** A typed record is skipped when its digest matches and every row it produced still holds the remembered hash. A generic record is skipped when its live (not removed) row carries a matching digest. A skipped record is still seen (so removal marks are unchanged), its rows count as `seen` and `unchanged`, its account is refreshed and its people are merged in the same order, as a full read would have counted them. A record that is an omission (it did not decode, map or encode) is never remembered, so it is decoded again and counted again on every sync.
- **Two records, one row.** Generic records whose keys scrub to the same key share one row. Only the first record of a row in a read may be skipped; every later record that maps to the same row is read in full, in the original order, so the row and the counts come out as a full read leaves them on every sync. For typed records, a record that produced a row some other record of the source also produced is remembered as contended and is never skipped, so the records that share a row are read in full together, as a full read reads them. The first sync that meets such a pair finds out by a guard: if a record read in full rewrites a row that a skipped record of the same run vouched for, the source is rolled back and read again in full from the same snapshot (one extra read, once); from the next sync on the pair is read in full from the start and the source is read once.
- **Forcing a full read.** `sync --full-read` or `TEAMSCRAWL_FULL_READ=1` reads every record of every source in full and still remembers, even a source whose fingerprint has not changed since the last sync (it does not stop at the fingerprint shortcut), so it checks the skipping exactly when the cache is stable. The archive is the same either way; use it to check. Under `watch`, the variable makes every sync that `watch` runs a full read.
- **Cost and bound.** About 16 bytes of digest per generic record plus a few bytes of redaction count, and per typed record its key, a 16-byte digest and 17 bytes per produced row plus the people it named: on a real cache of about 62,000 messages, 5,000 conversations, 1,000 activity items and 34,000 generic records, about 11 MiB (20,700 typed records, 10 MiB, most of it the people they named; 34,000 digests, under 1 MiB), 2.5% of a 765 MiB archive. The memory is bounded by the cache, not by the archive's age. A sync deletes the `typed_memo` rows of records that are no longer in the cache (in the same transaction; the archive rows they produced, and every `removed_at`, stay as they were, and a removed row never gets its mark cleared by this), and clears the digest of a generic row when it is marked removed (a record that returns is read in full). A read for one account (`--account`) forgets only within the databases it read. While a sync reads it holds the memory of one typed database at a time, the content hashes of the archive rows that memory names (looked up by rowid, never a whole table), and the digests of the live rows of one generic database: sized by the largest database in the cache, not by the archive. It avoids decoding the skipped records, so peak memory is lower, not higher.

**Consistency.** Teams keeps writing while teamscrawl copies. The copy order, the retry and the validation above give a self-consistent copy or a `snapshot_inconsistent` error. A truncated tail in the active log file (Teams was mid-write) is tolerated and counted as the omission `truncated_log_tail`. Because each source is one transaction, a reader never sees half a source. A source that fails leaves the archive as it was for that source, and the next sync retries it.

**Omissions.** A record teamscrawl cannot decode or map is skipped, counted by reason in `omissions`, and never guessed. A sync with at least one omission other than `denied_database` and `denied_store` (including `database_unreadable`) has status `ok_with_omissions` and still exits 0. The two denial codes count the credential denylist at work, not lost data, so they appear in `omissions` but never change the status.

| --- | --- |

### 4.2 The Outlook source (behind a flag)

With `--outlook-root` (or `TEAMSCRAWL_OUTLOOK=1`) the sync reads the new Outlook for Mac store as a second source, after every Teams source has finished. Each profile directory holding an `HxStore.hxd` is one source, `outlook|<profile>`, with calendar account `outlook/<profile>`. It is never part of a `--account` run, which names a Teams account. With Teams not installed (`teams_not_installed` or `no_teams_origin`), Outlook runs alone; when Teams discovery fails for any other reason the run fails before Outlook is tried. Outlook is on only because it was asked for, so having nothing to read is a failure: no profile under the root is the failed source `outlook` with code `no_outlook_profiles` (its fix names `<root>/<profile>/HxStore.hxd`, and says so when `HxStore.hxd` sits directly in the root), and a profile that cannot be examined is its own failed source (`no_full_disk_access` or `outlook_profile_unreadable`). Profiles of the old Outlook are listed in `outlook_classic_only`, a note and not a loss.

- **Read-only copy.** The store file is copied once into a private temporary directory (never the lock or side files) and read from the copy, which is removed on every exit. At most one copy is made per `OutlookMinReadInterval` (5 minutes, assumed), measured from the last attempted copy and kept in `meta`, so a failing store is not retried in a loop. A skipped read is the source status `skipped_interval` with `next_read_after`, and carries the omissions of the last read (a skip never hides a loss). A skip writes no `sync_runs` row. If the read before the skip failed, the skip is that failure again (the same status `failed` and code, a `failed` row in `sync_runs`, and the run is `partial` or `failed`) until a read succeeds. A last attempt later than the run's start (the clock moved back) does not hold the source off.
- **Fingerprint.** The file's size and modification time plus the store version byte, the reader version, the Outlook mapper version and the scrub rules version. An unchanged store reads nothing and reports the losses of its last read. A change to the mapper version reads an unchanged store again.
- **Guard.** `outlook_store_unrecognized`, `outlook_store_version` and `outlook_layout_unsupported` fail the Outlook source (a coded source failure; the run is `partial` when Teams committed) and apply nothing. A damaged-block share over 2% is the loss `outlook_blocks_damaged`; an event that does not map is `calendar_unmapped`; one the core refuses is `calendar_refused`. An all-day flag whose times fit no whole-day shape is stored with the flag unknown and counted as `calendar_all_day_unaligned` (not a loss).
- **Apply.** One transaction per profile: the events go through the calendar core under the calendar savepoint (a failure rolls the profile back and fails that source alone), covered days are the days on which the store holds at least one event that is not a series master (cumulative, in the machine's zone; a zone change takes the days of archived events again), and gone detection is off, so an event Outlook stops holding stays. `meta.outlook_read:<account>` keeps the census of the last good read (unknown layouts, blocks found and damaged, unmapped values; numbers only) for `calendar sources`, `meta.outlook_skipped:<profile>` says the last sync skipped the read because of the interval (the next sync that looks at the store forgets it), `meta.outlook_checked:<profile>` is when a sync last looked at the store, and `meta.outlook_derivation:<account>` stamps the mapper version, zone and scrub rules the profile was derived under; when it differs, each event of the batch is blanked before it is applied, so a stored value an older mapper wrote (an all-day flag stored as false) can become unknown instead of being kept over the unknown flag.
- **Apply.** One transaction per profile: the events go through the calendar core under the calendar savepoint (a failure rolls the profile back and fails that source alone), covered days are the days on which the store holds at least one event that is not a series master (cumulative, in the machine's zone; a zone change takes the days of archived events again), and gone detection is off, so an event Outlook stops holding stays. `meta.outlook_derivation:<account>` stamps the mapper version, zone and scrub rules the profile was derived under; when it differs, each event of the batch is blanked before it is applied, so a stored value an older mapper wrote (an all-day flag stored as false) can become unknown instead of being kept over the unknown flag.
- **Merged lists are unions.** A linked twin's attendee list and structured location (room) list are the union of the two copies' lists, not the list of the copy with the newer clock: in 67 of 67 real twins that carry both lists the Teams list is the longer, and the Outlook copy is the newer in 146 of 148, so choosing by clock hid attendees. Attendees match by lower-case address, or by lower-case display name when an entry has no address; rooms match by lower-case name, or by address when a room has no name. For an entry both copies hold, the response, type and role come from the copy whose list clock (the `attendees` or `location_list` field clock, else `detail_as_of`, else `last_modified`) is newer; an entry only one copy holds is kept. A list the union enlarged beyond the one the detail rule chose is named in `filled_fields` (`attendees`, `rooms`), and `attendee_count` is the merged length. Every other field keeps its clock rule. An event only one source holds, or whose other copy has no list, keeps its list verbatim.
- **Link.** An Outlook profile is its own principal until the operator links it. `--outlook-account <tenantId>/<userId>` (`TEAMSCRAWL_OUTLOOK_ACCOUNT`) links the profile to that Teams account with the method `config`; `none` ends the link. With more than one profile under the root, `--outlook-profile NAME` (`TEAMSCRAWL_OUTLOOK_PROFILE`) says which; `none` without a profile ends every link. The link is applied at the end of a sync, after the Teams sources, so the very first sync can name the account it creates, and it is kept in `calendar_account_links` (nothing is deleted: an unlink sets `unlinked_at`), so the flag is needed only to change it. Repeating a link that is in place, or ending one that is not, changes nothing. `none` also ends a link whose profile directory is gone: its profile names come from the archive's active links as well as from disk, and `--outlook-profile` may name one only the archive knows. The flags are read by the commands that sync or read the calendar and by no other (`whoami`, `status` and `version` ignore them); a value that came from `TEAMSCRAWL_OUTLOOK_ACCOUNT` alone while the Outlook source is off is a warning, and the same value as a flag is a `usage` error. With `--max-age 0` the implicit sync is off, so a link still waiting to be applied is a `usage` error whose fix is the `teamscrawl sync ...` command to run. A read command given the flag syncs first when the archive does not show the link as asked for. Only an explicit link ships; nothing links by overlap, because two people invited to one meeting hold the same events. A Teams account the archive has not seen, a malformed account, the flag without the Outlook source on, a profile name that is missing, unknown or needed, a Teams `--account` filter on a `sync` that links, and a second profile for an account that already has one are `usage` errors (exit 2) with a fix; the sources of that run are already committed, and `sync` still prints its report. Both sources key an event by its iCalUID, which Teams writes in lower-case hex and Outlook's store holds in upper case, so the Outlook mapper lower-cases it (and the series id it derives): that is what lets the twins meet. Linked, the Outlook rows are grouped under the Teams account: events both hold merge into one item with `sources: ["teams","outlook"]` and `filled_fields`, scalar fields by the clock rules and the attendee and room lists by union (below), an Outlook-only event gains the account's `tenant_id` and `user_id` and a new `event_id` (the id it had unlinked still resolves, and so does the linked id after an unlink, from the link history; an id some event has today wins over such an old one), a day either source covers is covered, and a meeting Teams marked gone stays hidden unless the Outlook copy was edited after the removal (section 3.2). Unlinked, `calendar --account <tenantId>/<userId>` omits the profile's events, an all-accounts agenda shows each twin once per principal, and the envelope names the profile in `unlinked_accounts` with the command that links it in `unlinked_fix`.

| `calendar sources [--account]` | Coverage and freshness, one row per account and source, Teams first. `{"items", "count", "truncated"}`; each item has `source` (`teams` or `outlook`), `account_id`, `principal` (the Teams account the row belongs to, or itself), `link` (`config` for an Outlook account joined to a Teams account by an explicit link, else `none`; a Teams row's `link` is always `none`, and a link shows on the Outlook rows whose `principal` is that Teams account), `tenant_id` and `user_id` (Teams rows), `window_start`, `window_end` (the first and last covered day; the window is a span, not a coverage claim, and for an Outlook row it can include days the store never showed, so `covered_days` is the claim), `covered_days` (the cumulative count of days the cache ever showed), `last_verified_at` (the newest verification of a covered day), `synced_at`, `cache_fresh_at`, `events_live`, `events_removed`, `events_with_detail`, `events_with_attendees`, `events_with_body`, `events_online`, `recaps_total` (every recap row of the account), `recaps_with_content` (recap rows with text or a live item; a row with neither, and the placeholders, which create no row, are not counted), `recaps_linked` (rows with an iCalUID, whether or not they have content), `recap_action_items` and `unknown_time_zones` (zone names for which no IANA id is known: Teams short names such as `FixtureUnknownSt`, Outlook codes as `code:<n>`; at most 50). Each row counts its own account, so linking an Outlook account never changes a Teams row. An Outlook row adds `status` (`ok`; `skipped_interval` when the last sync did not read because the minimum read interval had not passed; `unsupported_version`, `unsupported_layout` or `unreadable` when the last read failed, with `error` `{"code", "message", "fix"?}`), `last_read_at` (the last good read), `last_attempt_at` (the last copy of the store, good or not), `last_checked_at` (the latest sync that looked at the store at all, including a fingerprint check that found it unchanged and read nothing, so an idle store shows a recent `last_checked_at` and an old `last_read_at`, while a stalled sync shows an old `last_checked_at`; a skipped sync does not move it), `next_read_after` (only while the interval is running), `read_interval_seconds`, `unknown_layouts` (`[{"class", "tag", "count"}]`: only objects of a class the reader maps, the event class 0x6b and the detail class 0x6c, whose tag this build does not know, the sign that Outlook changed a layout; the store's other classes are not calendar objects and are never listed; empty on a healthy store), `blocks_invalid_ratio` (damaged blocks over blocks found in the last good read; a torn block is stale data, not harmless), `unmapped_values` (counts of event type, show-as and response values outside the mapped sets) and `deletions: "unverified"` (an event Outlook deleted may still be listed). A profile whose first read failed has a row with `error` and no counts. The census fields (`unknown_layouts`, `blocks_invalid_ratio`, `unmapped_values`) come from the last good read, also on a row that shows an `error`, and `census_as_of` says when that read was; a refused read's own layout is in `error.message`. An archive without the calendar tables gives an empty result with `needs_sync` and a hint. |
| `thread <conversation> <root-id>` | One thread, root first. Accepts a Teams message link instead of the two arguments (`.../l/message/<conversationId>/<messageId>`; a `parentMessageId` query parameter names the root). Also `--limit`, `--include-deleted`, `--include-system`, `--html`. |
| `conversations` | Conversations, newest activity first. `--kind`, `--team`, `--query` (ranked: exact name, then prefix, then substring, then all words; each group newest first), `--include-system`. Items add `member_count` and `read_horizon_at`; a Meeting conversation that live, non-master calendar events of the same principal name as their chat also gets `calendar_event_count` (distinct event keys; a cancelled occurrence is not counted, a declined one is, because the meeting happened) and `calendar_series_key` (the `series_key` the recurring occurrences share, absent when they belong to several series or are all single events). A chat no event names has neither key. |
| `teams` | The archived teams (a team is a conversation that other conversations name as their `team_id`), newest activity first. Items `{"tenant_id", "user_id", "team_id", "display_name", "channel_count", "last_activity_at", "unread_count"}`; `channel_count` excludes the team's own conversation, `last_activity_at` is the newest `last_message_at` over the team and its channels, and `unread_count` counts unread messages (section 3.2) in the team's channels and its own conversation, channels included. A `team_id` or `display_name` is what `--team` takes. Honors `--account`, `--limit` and `--fields`. |
| `people` | People seen as senders or members. `--query` is part of a display name or an exact id; use it to resolve `--from`. |
| `stores` | Every database and object store archived in `records`: items `{"database", "store", "records", "removed", "last_updated_at"}`, sorted by database then store. `records` counts live rows and `removed` rows no longer in Teams' cache. Honors `--account` (which hides databases whose name carries no account) and `--fields`. Not truncated. In text mode the `database` column shows the manager (`Teams:calendar-manager`) and a separate `account` column the shortened tenant and user ids; JSON carries the full name. Start here to find the `database` name `records` takes. |
| `records` | Archived generic records of one database. `--database` (required) is a database name or a prefix of one, matched case-sensitively from the start (`Teams:calendar-manager` matches every account's calendar database). Filters: `--store` (exact), `--since` (rows changed at or after it: a new or changed value, or a removal), `--account` (only rows whose database name carries that account; a database whose name carries no account is hidden by it, so use `stores` without `--account` to see them), `--include-removed` (records Teams' cache no longer holds, which have `removed_at`), `--limit` (default 50). Newest `updated_at` first. Items are record items (section 6.5). |
| `sql <query>` | One read-only `SELECT`, `WITH`, `EXPLAIN` or `VALUES` statement on a read-only connection. Result `{"columns", "rows", "count", "truncated"}`. It streams rows and stops reading at `--limit` (default 50), so `truncated` says more rows exist but there is no `total`. The statement is read as SQL tokens, so a word such as `attach` inside a string, comment or quoted name is harmless; a statement that is not a read, or a second statement, is a `usage` error, as is a query SQLite rejects (a typo, a missing table). Writes are impossible: the connection is read-only. It returns every account's rows regardless of `--account`. |
| `watch` | Runs until interrupted and streams JSON Lines (section 7). |
| `skill` | Prints the agent guide (the repository's `.agents/skills/teamscrawl/SKILL.md`, embedded in the binary) as raw Markdown on stdout, in every output mode, exit 0. It is a documented exception to the JSON default, like `--help`. It needs no archive and no Teams cache. |
| `metadata` | Prints the crawlkit app manifest (a `control.Manifest`: `schema_version`, `id` `teamscrawl`, `display_name`, `description`, `binary`, `paths` with the default database `~/.teamscrawl/teamscrawl.db` and `TEAMSCRAWL_DB`, the `status`, `sync` (`mutates`), `doctor` and `search` commands as `teamscrawl --json <command>`, `capabilities`, and `privacy` with `contains_private_messages: true`, `exports_secrets: false`, `local_only_scopes: ["teams_cache"]`) as one fixed-shape JSON document on stdout, indented in every output mode and regardless of `--format`, exit 0. It lets crawlkit's `crawlctl` discover teamscrawl. It needs no archive and no Teams cache, and never syncs. |
| `version` | Prints `{"version", "commit", "date"}` as one JSON document, or one human line (`teamscrawl <version> (commit <commit>, built <date>)`) in text mode. `teamscrawl --version` prints the same and exits 0. |

Filter values: `--since` and `--until` accept RFC3339, `YYYY-MM-DD` (local midnight) or a relative duration such as `90m`, `24h`, `7d`, `2w`. `--from` takes a person id or a case-insensitive part of a name. `--team` takes a team's exact name (case-insensitive for ASCII letters only) or its id; an unknown or ambiguous name is a `usage` error that lists the matches.

### 6.2 Streams and documents

- Results go to stdout. Progress, warnings, hints and the implicit-sync notice (section 6.4) go to stderr. Sync progress lines print only when stderr is a terminal.
- In JSON mode (including every non-TTY run) a command prints exactly one JSON document on stdout, compact on a pipe and indented on a terminal. Two exceptions: `watch` prints JSON Lines (section 7), and `skill` prints raw Markdown in every mode, as `--help` prints help text. `metadata` always prints one fixed-shape JSON document, indented in every mode, whatever `--format` says.
- Keys are snake_case and stable. Adding a field is compatible; renaming or removing one is a breaking change recorded in `CHANGELOG.md`. Optional fields are omitted when empty, except the always-present fields listed below. Times are RFC3339 UTC. Links keep a literal `&`.

### 6.3 List results

Every list command returns:

```json
{"items": [], "count": 0, "truncated": false, "archive_age_seconds": 0}
```

- `items` is always an array. `count` is its length. `--limit` (default 50, at least 1) caps it.
- `truncated` is true when more matches exist than were returned.
- `total` is the exact number of matches ignoring `--limit`. It is present only when `truncated` is true; otherwise `count` is the total. `sql` results never carry `total`.
- `channels_excluded: true` appears on `unread` and `messages --unread` when channels were left out; it is omitted when they are included.
- `archive_age_seconds` (below) and the optional `sync_error`, `needs_sync` and `hint` fields close the document.

### 6.4 Freshness and degraded answers

- `archive_age_seconds` is on every read result (the list commands, `sql`, `status`, `whoami`). It is the number of seconds since the covered accounts were last fully synced, or `null` when no complete sync covers them. "Covered accounts" means the one in `--account`, or, for a read of every account, the stalest account. Only a run in which every source succeeded (`ok`, `ok_with_omissions`, `unchanged`) refreshes an account; a partial or failed run refreshes nobody, and `sync --account X` refreshes only X.
- `needs_sync: true` and `"hint": "run teamscrawl sync"` appear together when there is no complete sync yet: the archive does not exist, has never synced, has only had partial or failed syncs, or was written by an older teamscrawl whose next sync upgrades it. An empty result then reads as "no data yet", not "nothing matched". They are omitted otherwise. In text mode the same hint also prints on stderr as a `hint:` line; in JSON mode there is no stderr hint, because the result carries it.
- If the implicit sync fails, the command still answers from the archive, prints the failure on stderr as `{"warning": {"code", "message", "fix"}}` (a `warning:` and a `fix:` line in text mode) and adds `"sync_error": {"code", "message"}` to the result. A partial implicit sync reports `partial_sync` the same way. Only cancellation by a signal turns it into an error.
- The implicit sync always covers every account, even with `--account`, so a filtered read never hides data from later reads. A held lock makes the implicit sync fail with `locked`, which becomes a `sync_error`.
- Reads work on an archive written by alpha.1 before its first upgrading sync; they treat it as having no complete sync yet.
- `--team` is validated before an implicit sync runs, so a mistyped team name fails fast. Its `usage` error names `teamscrawl teams`.
- When a read runs the implicit sync, it prints one line on stderr first. In text mode it is plain: `teamscrawl: syncing — archive is 2h14m old (max-age 15m)`, or `teamscrawl: syncing — no complete sync yet (max-age 15m)` for an archive that has never synced. In `json` and `log` mode it is one JSON line, so every stderr line stays machine-readable: `{"notice":"syncing","reason":"stale","archive_age_seconds":N,"max_age_seconds":N}` (`reason` is `stale` or `never_synced`; `archive_age_seconds` is omitted when never synced). The result then carries `"synced": {"seconds": N, "status": "..."}` beside `archive_age_seconds` (`seconds` is how long the sync took, `status` the sync report's status: `ok`, `ok_with_omissions`, `unchanged`, `partial` or `failed`; for `whoami` also inside `archive`). Neither the line nor `synced` appears when the archive was fresh enough or `--max-age` is 0, and the line never goes to stdout. A failed or partial sync still adds `sync_error` and the warning.

### 6.5 Item shapes

Message items (`messages`, `search`, `unread`, `thread`; also `watch` message lines):

| Field | Rule |
| --- | --- |
| `tenant_id`, `user_id`, `conversation_id`, `conversation_display_name`, `id`, `sender_id`, `sender_name`, `sent_at`, `message_type`, `text` | Always present. `sender_name` and `text` may be empty strings. |
| `mentions_me`, `pinned` | Always present, `false` included. |
| `mention_kind` | Present only when `mentions_me` is true: `person` (you by name), `channel`, `team`, `tag`, `everyone` (a broadcast) or `other` (a kind this version does not know). See section 3.2. |
| `reply_chain_id`, `parent_message_id`, `importance`, `link` | Present when known. `link` is a Teams deep link `https://teams.microsoft.com/l/message/<conversationId>/<messageId>?tenantId=...`; a reply's link adds `parentMessageId`. |
| `edited_at`, `deleted_at`, `mentions`, `reactions`, `files`, `links`, `subject`, `html`, `text_truncated` | Omitted when empty or false. `html` appears only with `--html`. |
| `reply_count`, `last_reply_at` | Channel thread roots only. `reply_count` is the number of live replies stored for the root, computed at query time from archived replies, so it can be lower than Teams shows if the cache never held the replies. A root nobody answered has `reply_count: 0` and no `last_reply_at`. A message with no `reply_count` key (a reply, any chat message) is not a channel root. |

`mentions` items are `{id, display_name}`; `reactions` items `{key, count, user_ids?}`; `files` items `{name, url?, type?}`.

Conversation items: `tenant_id`, `user_id`, `id`, `kind`, `display_name`, `member_count` and `favorite` are always present; `title`, `team_id`, `last_message_at` and `read_horizon_at` are omitted when empty.

Person items: `tenant_id`, `id`, `display_name`, and `last_seen_at` when known.

Team items (`teams`): `tenant_id`, `user_id`, `team_id`, `display_name`, `channel_count` and `unread_count` are always present; `last_activity_at` is omitted when no message time is known.

Store items (`stores`): `database`, `store`, `records` and `removed` are always present; `last_updated_at` is omitted when unknown.

Record items (`records`): `source`, `database`, `store`, `key_json`, `first_seen_at` and `updated_at` are always present; `tenant_id` and `user_id` are omitted when empty; `removed_at` is omitted for a live record; `value_json` is omitted when the value never decoded. `key_json` and `value_json` are the parsed JSON itself (a string key is a JSON string, an object value a JSON object), not strings holding JSON. Bytes appear as `{"$bytes": "<base64>"}`. With `--max-text N`, a `value_json` whose JSON text is longer than N characters is replaced by a JSON string of its first characters plus `…`, and `text_truncated` is true; when `--fields` includes `value_json`, `text_truncated` stays with it.

Activity items: `tenant_id`, `user_id`, `id`, `type`, `is_read`, `at`, `conversation_display_name`, `sender_name` and `text` are always present; `subtype`, `conversation_id`, `message_id`, `reply_chain_id`, `app_id`, `sender_id`, `message_sent_at`, `text_truncated`, `link`, `actor_id`, `actor_name` and `actor_inferred` are omitted when empty or false. `sender_*` is always the related message's author. `actor_id` and `actor_name` say who did the thing, by type: `reaction` and `reactionInChat` name the reactor on a best-effort basis: the user, other than the account (whose id is taken as `8:orgid:<user_id>`, the `self_id` of `whoami`), whose reaction with the item's subtype key is nearest in time to the item, read from the message's reactions. It can name the wrong person when several people used the same key at about the same time, or when a reaction was removed, so these items carry `actor_inferred: true`; `mention`, `mentionInChat`, `reply`, `replyToReply` and `follow` name the related message's sender; `msGraph`, `teamMembershipChange` and `threadActivity` have no actor in the data, so the fields are omitted, as they are whenever the related message is not archived. `actor_name` comes from the people table and is omitted when the name is not known. Activity types seen in real caches: `mention`, `mentionInChat`, `reply`, `replyToReply`, `follow`, `reaction`, `reactionInChat`, `msGraph`, `teamMembershipChange`, `threadActivity`. An unknown `--type` matches nothing and is not an error.

### 6.6 `--fields`, `--max-text` and `text_truncated`

- `--fields a,b,c` keeps only those top-level keys of each item, in the order given. An unknown key is a `usage` error that lists the valid keys for that command. On `watch`, a key valid for either a message or an activity item is accepted. The list envelope keys (`count`, `truncated`, `total`, `archive_age_seconds`, ...) are never projected away.
- `--max-text N` cuts each item's `text` to N characters, counting the trailing `…` the cut adds (the cut may fall mid-word), and sets `"text_truncated": true` on the cut items. `0` keeps all text. A negative value is a `usage` error: `--max-text=-1` prints `--max-text must be 0 or more`, and `--max-text -1` (separate argument) is rejected by the argument parser with `--max-text: expected int value but got "-1" ...`. When `--fields` includes `text`, `text_truncated` stays with it.

## 7. `watch`

`watch [--every 60s] [--min-interval 60s] [--emit-initial]` keeps the archive current and tells the caller what changed. It is the one command that prints more than one JSON document: it prints **JSON Lines**, one compact object per line on stdout, flushed as each event happens. Every line has a `kind`.

How it runs:

1. It syncs once at start. By default that first sync is a silent baseline: its changes are not printed, so only later changes appear. `--emit-initial` prints them too.
2. It watches the Teams `.leveldb` and `.blob` directories with file-system events (kqueue on macOS). Events are debounced: a sync starts after the cache has been quiet for 2 seconds and at most 10 seconds after the first event of a burst, but never sooner than `--min-interval` (default 60 seconds, env `TEAMSCRAWL_WATCH_MIN_INTERVAL`, `0` disables the pause) after the previous sync ended. Teams on a busy account writes its cache continuously, and a sync is a full read, so without the pause `watch` would sync back to back and keep a CPU core busy. Events that arrive during a sync or during the pause coalesce into one sync when the pause ends, and no sync runs if the cache did not change; the first sync at start is immediate, a stop signal during the pause exits at once, and a sync that fails because the archive is locked is retried after the short lock backoff, not after the pause. A negative `--min-interval` is a `usage` error. Consequently the archive can lag Teams by up to `--min-interval` plus the time a sync takes. A poll every `--every` (default 60 seconds) is the safety net when events are missed; it syncs only when the source fingerprint changed (a sync that runs with `TEAMSCRAWL_FULL_READ=1` set is a full read of every record). If file events are unavailable, `watch` warns on stderr and polls.
3. It runs until SIGINT or SIGTERM, then exits 0.

Line kinds:

| `kind` | Shape | When |
| --- | --- | --- |
| `message` | `{"kind": "message", "change": "new" \| "edited" \| "deleted", "item": <message item>}` | A message was inserted, changed or newly tombstoned by a sync. |
| `activity` | `{"kind": "activity", "change": "new" \| "edited", "item": <activity item>}` | An activity item was inserted or changed. |
| `sync` | `{"kind": "sync", "report": <sync report>}` | After each sync that ran and emitted, one line, after that sync's change lines. |
| `migrated` | `{"kind": "migrated", "from": 1, "to": 2, "rows": N}` | The first sync upgraded an older archive. Printed before anything else, even for a silent baseline. It is not a change: no `edited` lines follow for those rows. |
| `error` | `{"kind": "error", "error": {"code", "message", "fix"}}` | A sync or check failed with a runtime error, including `partial_sync`. Watching continues, and an unchanged repeat of the same failure is reported once. |

`item` has the same shape as the matching `messages` or `activity` item and honors `--fields`, `--max-text` and `--account`. System pseudo-conversations are skipped. `change: "deleted"` means the message gained its `deleted_at`.

Partial syncs: when a sync commits some sources and fails others (`partial_sync`), `watch` first emits the changes of the committed sources and a `sync` line with `"status": "partial"`, then the `error` line. The fingerprints stay as they were, so the next pass retries only what failed and no change is lost. The first sync that commits anything is the baseline, exactly as for a normal first sync: its changes are printed only with `--emit-initial`. `--fields html` fills `html` as `messages --html` does.

Failures: a held lock prints a `locked` warning on stderr and retries after at most 5 seconds. Environment errors (`teams_not_installed`, `no_full_disk_access`, `no_teams_origin`, `archive_newer`) end the run with a plain error on stderr and exit 3. If the first sync fails and a later one succeeds, that later sync is taken as the baseline, its changes are not printed, and a `baseline_delayed` warning on stderr says so (its `fix` suggests reading the archive, or restarting with `--emit-initial`). In text mode (`--format text`) `watch` prints one human line per event instead of JSON.

Latency: a change reaches the output after Teams flushes it to its cache, plus the debounce (2 to 10 seconds) and one sync. Measured on a real cache, a message's sent time to its line took about 12 to 32 seconds (median about 17 seconds), most of it Teams' own flush delay.

## 8. Privacy and security

- **Read-only by construction.** There is no code path that writes to Teams' storage. The Teams cache is only ever opened for reading, and `sql` runs on a read-only database connection (writes, `ATTACH` and multi-statement queries are rejected before and by the connection).
- **No credentials, no network.** teamscrawl never reads Teams tokens. Databases and object stores whose names match the denylist (section 2, which includes `Teams:auth:*`) are never opened for values or decoded, and values of other records are scrubbed of token-shaped material before they are archived: JWT-shaped substrings, the whole value (of any type) of any object key, or any V8 Map pair key, named `access_token`, `refresh_token`, `id_token`, `authorization`, `client_secret` or `password` (ignoring case), any string starting with `Bearer ` (ignoring case), and the value of a `sig=` query parameter in a URL (ignoring case), each replaced by `[redacted]`; record keys are scrubbed the same way, and two record keys that differ only in scrubbed material collapse into one row (over-redaction, never a leak). Credentials inside a string that holds JSON (up to four levels) and the `value` field of an object whose `type`, `name` or `key` field is one of those names are redacted too, and each sync clears (like the denylist purge) archived rows whose key changes when scrubbed. The sync report counts these in `redacted` (a count, not an omission). Message text in the typed tables is not scrubbed. The program has no network code.
- **The archive holds message content verbatim.** That includes anything people pasted into a message: links with tokens or secrets, credentials, file names, customer data. `raw_json` keeps the full original record. Treat the archive like the chats it contains: do not commit it, sync it to shared storage or paste its contents into tools you would not show the original messages to.
- **File permissions.** On macOS the archive file and its `<db>.lock` file are mode 0600 and the default archive directory `~/.teamscrawl` is mode 0700. On Windows the archive directory is the privacy boundary: the default `%LOCALAPPDATA%\teamscrawl` directory (or `%USERPROFILE%\AppData\Local\teamscrawl` when `LOCALAPPDATA` is unset) is secured before open. An existing custom `--db` parent must already grant only the current user and SYSTEM, with both effective access and object/container inheritance that propagates to children for each trustee. The macOS-style `~/.teamscrawl` directory is a custom parent on Windows and is never silently secured. Before SQLite opens, any existing archive, WAL (`<db>-wal`), shared-memory (`<db>-shm`), and rollback-journal (`<db>-journal`) files must already be private; unsafe files fail with `db_error` without rewriting their ACLs. Missing companions inherit the private directory boundary when SQLite creates them.
- **Snapshots.** The temporary copy of the cache includes Teams' sign-in database. It lives in a private temp directory for the length of one source's sync (mode 0700 on macOS, current-user + SYSTEM ACL on Windows) and is removed on success, on failure, and on SIGINT or SIGTERM. Stale snapshot directories older than one hour are removed at the start of every sync.
- **Full Disk Access** is required only on macOS (see [docs/full-disk-access.md](docs/full-disk-access.md)). On Windows the default Teams cache lives under LocalCache and is not TCC-protected.
- **Tests and docs use synthetic data only.** The committed fixture is written by a real browser from made-up records.

## 9. Known limits

- teamscrawl sees only what the desktop app has cached. History the user never scrolled to may be missing, and Teams evicts old messages from its cache, so the archive is complete only from the first sync that saw a message onward. Sync regularly (`--max-age` does it for you).
- macOS and Windows with the new Teams app are supported. Classic Teams and Linux are not. Contact stores, call history and pinned-message lists are mirrored only as raw `records` (canonical JSON of what the cache holds) until typed tables or mappers exist.
- The calendar holds only what Teams cached. Teams caches the days the user looked at, not a range, so coverage is a set of days (`calendar_covered_days`); a day it never showed is unknown, not empty. Attendees, body and rooms exist for the minority of events the user opened. Recaps expire in Teams (`expires_at`). A day on which every event was deleted vanishes from the cache and reads as eviction, so its deleted events stay live. `teamscrawl calendar`, `teamscrawl calendar event` and `teamscrawl calendar actions` read it; `sql` on the `calendar_*` tables also works.
- An explicit Outlook link says the whole profile belongs to that Teams account. If a profile also holds a shared or delegate calendar (not yet known), its events appear as the account's own after the link. Whether Outlook shows a deleted or cancelled event in its store is unverified, so gone detection is off for Outlook: an event deleted in Outlook stays in Outlook-only agendas, and a linked twin is hidden only by a Teams removal. A meeting Teams removed shows again when the Outlook copy was modified more than 5 seconds after the removal, so an edit made in Outlook, such as a response or a category change, can bring back a meeting Teams removed; the rule is kept on purpose, because an edit is evidence the meeting still exists. Outlook covers the days on which its store holds at least one event, so a day with no event reads as `coverage_gap` even where Outlook may be authoritative.
- Full Disk Access is required only for the app that runs teamscrawl on macOS.
- Read-only: no sending, reacting or marking read. Attachments and media are not downloaded.
- `reply_count` and `last_reply_at` are counted from archived replies and can lag Teams.
- People display names follow the most recent sighting; after an archive upgrade a few can differ from what a fresh sync would give.
- Teams can change its storage layout at any time. teamscrawl then fails with a named error or reports counted omissions; it never guesses. A new V8 wire version fails with the version.
- A multi-source sync is atomic per source, not per run: a `partial` sync leaves the committed sources in the archive (section 4).
- Some `msGraph` activity rows (Microsoft 365 notices) have an empty conversation, sender and text: the cache holds no message for them, so they have no `actor_*` either.
- `needs_sync` is advisory: a read of a never-synced archive with `--max-age 0` exits 0 with an empty result and `needs_sync: true`. Check for it before reading an empty result as "no match".
- Untitled group chats are named after a few members (`Ana, Ben, Chao +2`), so two chats with the same first members can share a name; select such a chat by `conversation_id`.
- `watch` latency is dominated by when Teams writes its cache, not by teamscrawl.
- macOS release binaries are Developer ID signed and notarized only when the release was built with the Apple signing secrets; the release notes of each release say which. Windows release binaries are intentionally unsigned.

## 10. Versioning and compatibility

- The JSON contract in section 6 is stable within 0.x releases except where `CHANGELOG.md` records a break. Fields may be added; error codes, omission codes and activity types may be added.
- The archive has two version numbers: the SQLite schema version (5) and the derivation version (2, section 3.2). An older archive is upgraded in place by the first `sync`; the schema 5 upgrade adds the calendar tables, and an older teamscrawl cannot open such an archive (`archive_newer`). An archive written by a newer build is refused for writing with `archive_newer`.
- The source fingerprint includes a decoder version; raising it makes the next sync re-read an unchanged cache, and the read memory signature includes it too, so that re-read decodes every record in full (section 4.1).
